# drevo — Embedded Graph Database for Knowledge Management

A lightweight, embeddable graph database written in Rust. Designed as the storage engine for cross-platform knowledge-base applications (similar to Obsidian), drevo runs natively on desktop (via FFI/Tauri), mobile (iOS/Android via C bindings), and in the browser (via WebAssembly). It also ships as a standalone HTTP server for containerised deployments.

> **📖 User documentation lives in [`docs/`](docs/)** — start with the [User Guide](docs/user-guide.md), then the [Cypher Reference](docs/cypher-reference.md), [SDK Reference](docs/sdk-reference.md), [Admin Guide](docs/admin-guide.md), and [Migration Guide](docs/migration-guide.md). This README is the design-and-roadmap companion to those guides.

## Use Cases

drevo is the storage engine for a cross-platform graph notebook. Target scenarios:

### CBT Journal (Cognitive Behavioral Therapy)

Nodes: `thought`, `emotion`, `situation`, `cognitive_distortion`, `rational_response`. Edges: `triggered_by`, `leads_to`, `challenges`, `reframed_as`. The graph enables tracing chains of thoughts and finding recurring distortion patterns via traversal.

### Scenario / Book / Story Editor

Tree-structured narratives: nodes are `chapter`, `scene`, `character`, `location`, `plot_point`. Edges: `contains`, `follows`, `involves`, `takes_place_in`. Subgraph extraction gives a complete context for a scene. MCP integration allows AI agents to read/write the graph for co-authoring.

### IT Task Manager

Nodes: `task`, `epic`, `sprint`, `developer`, `component`. Edges: `assigned_to`, `blocks`, `part_of`, `depends_on`. BFS from a blocked task reveals the full dependency chain. Kind index enables board views (all tasks in a sprint).

### ERP System

Nodes: `order`, `product`, `customer`, `warehouse`, `invoice`. Edges: `ordered_by`, `contains`, `stored_in`, `billed_to`. Transactions ensure consistency when updating order status and inventory simultaneously.

### Bug Tracker / Control System

Nodes: `bug`, `feature`, `release`, `test_case`, `assignee`. Edges: `reported_in`, `fixed_by`, `verified_by`, `blocks_release`. FTS over bug descriptions, traversal for impact analysis.

### Common patterns across all scenarios

- **Node kinds** define domain entities — the `kind` field + `kind_index` provide filtered views
- **Edge kinds** define relationships — `scan_prefix` retrieves all edges of a given type
- **Properties** (HashMap) store domain-specific metadata without schema migration
- **FTS** enables search across all content (titles, bodies, properties)
- **Subgraph** extraction provides bounded context for AI agents (MCP)
- **Transactions** ensure consistency for multi-step operations
- **Cross-platform**: all scenarios must work identically on desktop, mobile (iOS/Android), and WASM

## Long-term Vision: Graph-Vector Database

Beyond the embedded knowledge-base use case described above, drevo is on a multi-phase trajectory toward becoming a full graph-vector database with capabilities equivalent to Neo4j and Memgraph:

- **Cypher query language** — full support for CREATE / MATCH / MERGE / SET / DELETE / WHERE / RETURN / WITH / aggregations / variable-length paths (Phase 10)
- **Bolt wire protocol** — Neo4j-compatible, so `cypher-shell`, `neo4j-python-driver`, and `neo4j-javascript-driver` connect out of the box (Phase 11)
- **Native vector search** — `Value::Vector` type, HNSW index, joint graph+vector queries for RAG and semantic search (Phase 12)
- **MVCC concurrency** — readers never block writers, multiple configurable isolation levels (Phase 13)
- **Cost-based query planner** — statistics, cardinality estimates, plan caching, supernode handling (Phase 14)
- **Production ecosystem** — MCP server, web UI, Python SDK, replication, streaming ingestion, CDC, RBAC, observability (Prometheus `/metrics`, structured query log) (Phase 15)
- **Keyword analytics & lexical search** — BM25 ranking, `keywords()` extraction from properties/labels, similarity-collapsed faceted group-by-keyword (Phase 17)

Phases 1-9 (embedded DB + HTTP API + Docker) form the foundation. Phases 10-15 layer the query language, protocol, vector engine, concurrency, optimizer, and ecosystem on top of the existing storage and traversal engine — without rewriting it.

## Inspirations

drevo borrows architectural ideas from two existing graph databases. Their licenses prevent direct reuse, but we adopt their proven designs:

| Database | What we borrow | Why we cannot use it directly |
|----------|---------------|-------------------------------|
| **[HelixDB](https://github.com/HelixDB/helix-db)** | graph+vector native engine, compiled query plans, MCP tooling, memory-mapped storage, built-in embeddings | BSL (Business Source License) — incompatible with MIT |
| **[Memgraph](https://github.com/memgraph/memgraph)** | full Cypher support, Bolt protocol, MVCC, in-memory + WAL/snapshots, MAGE plugin system, Python query modules, streaming ingestion | AGPL / proprietary enterprise — incompatible with MIT |

drevo ships under MIT (see License section).

## Core Requirements

### Platform targets

- `x86_64-unknown-linux-gnu`
- `x86_64-apple-darwin` / `aarch64-apple-darwin`
- `x86_64-pc-windows-msvc`
- `aarch64-apple-ios` / `aarch64-linux-android`
- `wasm32-unknown-unknown` (browser, Tauri v2 WASM)

### Deployment targets

- **Embedded (in-process)**: Tauri desktop, iOS/Android via C FFI, browser via WASM
- **Containerized (server mode)**: Docker image with HTTP API, Kubernetes-ready
  - Official Docker image published to registry (like PostgreSQL, Redis, Neo4j)
  - Helm chart / K8s manifests for orchestrated deployments
  - Volume-based persistence (`/data`), health checks, graceful shutdown

### Non-goals

- No SQL compatibility layer
- No distributed/cluster support
- No ACID transactions across network

## Data Model

### Node

```
id:         u64            (auto-increment, unique)
uuid:       [u8; 16]       (UUID v7, sortable, globally unique)
kind:       String         (e.g. "note", "tag", "person", "concept")
title:      String
body:       String         (raw Markdown)
body_html:  String         (rendered, cached)
created_at: i64            (Unix ms)
updated_at: i64            (Unix ms)
properties: HashMap<String, Value>   (arbitrary JSON-compatible metadata)
```

### Edge

```
id:         u64
uuid:       [u8; 16]
from_id:    u64            (source node)
to_id:      u64            (target node)
kind:       String         (e.g. "links_to", "tagged_with", "derived_from", "alias_of")
weight:     f32            (default 1.0, used for ranking/traversal)
created_at: i64
properties: HashMap<String, Value>
```

### Index entries (internal)

- `title_idx`:    `BTreeMap<String, u64>`
- `kind_idx`:     `BTreeMap<String, Vec<u64>>`
- `fts_idx`:      inverted index over `title + body` (trigram or BM25)
- `updated_idx`:  `BTreeMap<i64, u64>` (for recent notes)

## Storage Engine

### File layout

```
<vault_dir>/
  drevo.db          <- single binary file (redb)
  drevo.db.lock     <- advisory lock
  drevo.db.wal      <- write-ahead log (optional, for crash recovery)
```

### Backend: redb

[redb](https://github.com/cberner/redb) — pure Rust, no C dependencies, ACID transactions, WASM-compatible, actively maintained.

Alternative if redb has WASM issues: [sled](https://github.com/spacejam/sled).

### Storage abstraction trait

```rust
pub trait StorageBackend: Send + Sync {
    fn get(&self, key: &[u8]) -> Result<Option<Vec<u8>>>;
    fn put(&self, key: &[u8], value: &[u8]) -> Result<()>;
    fn delete(&self, key: &[u8]) -> Result<()>;
    fn scan_prefix(&self, prefix: &[u8]) -> Result<Vec<(Vec<u8>, Vec<u8>)>>;
    fn flush(&self) -> Result<()>;
}
```

Two backends planned: `MemoryBackend` (BTreeMap) and `RedbBackend` (ACID, B-tree).

### Tables in redb

```
nodes:       u64 -> bincode(Node)
edges:       u64 -> bincode(Edge)
node_uuid:   [u8;16] -> u64
edge_uuid:   [u8;16] -> u64
out_edges:   u64 -> Vec<u64>      (adjacency list: from_id -> edge_ids)
in_edges:    u64 -> Vec<u64>      (reverse: to_id -> edge_ids)
kind_index:  String -> Vec<u64>
title_index: String -> u64        (exact title lookup)
fts_index:   String -> Vec<u64>   (trigram -> node_ids)
meta:        String -> Vec<u8>    (schema version, stats)
```

## API Surface (Rust)

```rust
pub struct Drevo { /* opaque */ }

impl Drevo {
    // Lifecycle
    pub fn open(path: &Path) -> Result<Self>;
    pub fn open_in_memory() -> Result<Self>;
    pub fn close(self) -> Result<()>;
    pub fn compact(&self) -> Result<()>;

    // Node CRUD
    pub fn create_node(&self, node: NewNode) -> Result<Node>;
    pub fn get_node(&self, id: u64) -> Result<Option<Node>>;
    pub fn get_node_by_uuid(&self, uuid: Uuid) -> Result<Option<Node>>;
    pub fn get_node_by_title(&self, title: &str) -> Result<Option<Node>>;
    pub fn update_node(&self, id: u64, patch: NodePatch) -> Result<Node>;
    pub fn delete_node(&self, id: u64) -> Result<()>;

    // Edge CRUD
    pub fn create_edge(&self, edge: NewEdge) -> Result<Edge>;
    pub fn get_edge(&self, id: u64) -> Result<Option<Edge>>;
    pub fn update_edge(&self, id: u64, patch: EdgePatch) -> Result<Edge>;
    pub fn delete_edge(&self, id: u64) -> Result<()>;

    // Graph traversal
    pub fn neighbors(&self, node_id: u64, direction: Direction, kind: Option<&str>) -> Result<Vec<Node>>;
    pub fn edges_of(&self, node_id: u64, direction: Direction) -> Result<Vec<Edge>>;
    pub fn shortest_path(&self, from: u64, to: u64) -> Result<Option<Vec<u64>>>;
    pub fn subgraph(&self, root: u64, depth: u8) -> Result<SubGraph>;

    // Search
    pub fn search_fts(&self, query: &str, limit: usize) -> Result<Vec<ScoredNode>>;
    pub fn list_nodes_by_kind(&self, kind: &str, limit: usize, offset: usize) -> Result<Vec<Node>>;
    pub fn list_recent(&self, limit: usize) -> Result<Vec<Node>>;

    // Batch / transactions
    pub fn transaction<F, T>(&self, f: F) -> Result<T>
    where F: FnOnce(&mut Txn) -> Result<T>;

    // Export / import
    pub fn export_json(&self, writer: &mut dyn Write) -> Result<()>;
    pub fn import_json(&self, reader: &mut dyn Read) -> Result<ImportStats>;
    pub fn export_graphml(&self, writer: &mut dyn Write) -> Result<()>;
}

pub enum Direction { Outgoing, Incoming, Both }

pub struct SubGraph {
    pub nodes: Vec<Node>,
    pub edges: Vec<Edge>,
}

pub struct ScoredNode {
    pub node: Node,
    pub score: f32,
}
```

## Full-Text Search

Trigram index (simple, no external deps, WASM-safe):

- On `create_node` / `update_node`: tokenize `title + body` into trigrams, store `trigram -> Vec<node_id>` in `fts_index`
- On `search_fts(query)`: extract query trigrams, intersect posting lists, rank by TF-IDF or hit count
- Normalize: lowercase, strip punctuation, CJK character support

Optional phase 2: integrate [tantivy](https://github.com/quickwit-oss/tantivy) for BM25 scoring (desktop only, not WASM).

## Serialization

**bincode v2** for all stored values — compact binary, fast encode/decode, deterministic, serde-compatible.

`properties: HashMap<String, Value>` — use `serde_json::Value` to allow arbitrary metadata without schema migration.

## Error Handling

```rust
#[derive(thiserror::Error, Debug)]
pub enum DrevoError {
    #[error("storage error: {0}")]
    Storage(#[from] redb::Error),
    #[error("serialization error: {0}")]
    Serialization(#[from] bincode::error::EncodeError),
    #[error("node not found: {0}")]
    NodeNotFound(u64),
    #[error("edge not found: {0}")]
    EdgeNotFound(u64),
    #[error("duplicate title: {0}")]
    DuplicateTitle(String),
    #[error("database locked")]
    Locked,
    #[error("io error: {0}")]
    Io(#[from] std::io::Error),
}

pub type Result<T> = std::result::Result<T, DrevoError>;
```

## Phase Plan

Development is split into two milestones:

- **PoC** — a fully functional embedded graph DB that can power the notebook app on all platforms (desktop, mobile, WASM). After PoC, the notebook can be built and used.
- **MVP** — a distributable product: Docker image, HTTP API, Kubernetes support. After MVP, drevo can be deployed as a standalone service (like PostgreSQL or Redis).

```
PoC: Phases 1-6    →  notebook can be built on top of drevo
MVP: Phases 7-9    →  drevo ships as a Docker/K8s product
```

- [x] `00053` WAL / crash recovery — `src/db.rs` adds a documented crash-recovery model on top of redb's per-commit double-write+fsync (which is the WAL — each `RedbBackend::put`/`delete` is its own committed redb transaction with double-write+fsync inside the on-disk format). The pre-`00053` defect was an **id-counter durability gap**: `Drevo::create_node` / `create_edge` bumped an in-memory atomic counter on every allocation but only persisted `meta:next_node_id` / `meta:next_edge_id` via `Drevo::close()`. A process killed between two `create_node` calls therefore rewound the persisted counter on next open, and the very next `create_node` reused an already-stored id — `node:<id>` got silently overwritten and the title / UUID / kind indexes drifted out of sync. **Fix:** `Drevo::load_counters` now performs a max-id rescan at every `Drevo::open` — reads the persisted hint, scans `max(stored_id)` from the `node:` and `edge:` prefixes, and takes `max(persisted, scanned + 1)` as the effective counter. The persisted value becomes a *hint*, the on-disk rows are the source of truth; the rescan is O(N) over data-row keys (the per-key length guard filters `node_uuid:` / `node_kind:` / etc. so the cost is data-only, not all-keys). - [x] `00135` **`UNWIND` — list → rows expansion** — `UNWIND list AS x` expands a list expression into one binding row per element, carrying every existing binding forward (so each input row is multiplied by the list) and binding `x` to the element. It is the complement of `collect` (aggregation does rows → list; `UNWIND` does list → rows) and the join point that lets one query iterate a caller-supplied / derived list alongside graph reads. Semantics mirror Neo4j: an **empty list and `null` both expand to zero rows** (so a heterogeneous scan does not abort), a **non-list scalar is a recoverable [`ExecError::TypeMismatch`]**, and element order is preserved. It composes everywhere a binding row flows — feeding `WITH` + aggregation (`UNWIND keywords(n.body, 5) AS kw … RETURN kw, count(*)`, the faceting idiom `00132`/`00133` assumed), feeding `CREATE` (one node/edge per element), stacking (`UNWIND … UNWIND …` = Cartesian product), and correctly yielding nothing after a `MATCH` that produced no rows. Semantics mirror Neo4j: the right-hand side is compiled as a regular expression and the **entire** left-hand string must match (Java `Matcher::matches`, not `find`), so an anchor-free pattern is implicitly anchored at both ends (`'hello world' =~ 'hello'` is `false`). `NULL` on either side yields `NULL` under three-valued logic (so a row whose property is absent never satisfies a `WHERE` predicate — the heterogeneous-scan discipline shared with `00077`/`00138`); a non-string operand is a recoverable [`ExecError::TypeMismatch`]; a malformed pattern (or one that exhausts the matcher's backtracking budget) is the new recoverable [`ExecError::InvalidRegex`] (mapped to a Bolt `SEMANTIC_ERROR`). **No new dependency:** rather than pull the `regex` crate into the production tree (which `Cargo.toml` deliberately keeps out), the operator is backed by a small hand-rolled backtracking engine ([`cypher::regex`](src/cypher/regex.rs)) in the project's dependency-free tradition (FTS tokenizer, Porter stemmer, BM25, HNSW, planner). It covers the Java/Neo4j subset real Cypher uses — literals, `.`, the quantifiers `* + ? {n} {n,} {n,m}` (greedy or lazy), character classes with ranges / negation / the `\d \D \w \W \s \S` shortcuts, anchors, alternation, grouping `(...)` / `(?:...)`, and the inline `(?i)` case-insensitive flag — and bounds catastrophic backtracking with a per-match step budget. Implementation is purely additive on top of `00063`: [`regex_match`](src/cypher/executor.rs) replaces the `Unsupported` stub in `eval_binary`, and the two upfront `validate_expr_supported` sweeps stop pre-rejecting `=~`. Tests: 28 inline unit ([`cypher::regex`](src/cypher/regex.rs): anchoring, quantifiers, classes, shortcuts, alternation, groups, escapes, `(?i)`, Unicode, malformed-pattern errors, bounded backtracking, zero-width-repeat termination) + 19 integration in [`tests/cypher_regex_match_tests.rs`](tests/cypher_regex_match_tests.rs) across the five scenario domains (CBT should-statements, story chapter titles, task ticket IDs, ERP SKU codes, bug-reporter emails) plus three-valued logic, type / invalid-regex errors, parameterised patterns, and projection. Docs: `=~` graduates from the [Cypher reference](docs/cypher-reference.md) "Not yet supported" table to a worked `WHERE` subsection, and the [migration guide](docs/migration-guide.md) Neo4j-parity table flips it to ✅.
- [x] `00142` **Aggregations nested inside a `CASE` arm** — folds an aggregation (`count`, `sum`, `avg`, `min`, `max`, `collect`) that appears in any arm of a `CASE` expression (the scrutinee, a `WHEN`, a `THEN`, or the `ELSE`) over the current group, closing the last named `CASE` gap left open by `00137`. Before this task the projection validator checked `CASE` sub-expressions with the non-aggregation validator and [`eval_with_agg`](src/cypher/executor.rs) did not recurse into a `CASE`, so `RETURN CASE WHEN count(*) > 5 THEN 'overloaded' ELSE 'normal' END` returned [`ExecError::Unsupported`]. - [x] `00143` **Anonymous head / intermediate nodes in `MATCH`** — a pattern whose **head** (first) node, or any non-final **intermediate** node, carries no variable — `MATCH (:Person)-[:KNOWS]->(b)`, `MATCH ()-[:KNOWS]->(b)`, `MATCH (a)-->()-->(c)` — is ordinary, extremely common Cypher that the parser has produced since `00062`. ### Phase 10.5 — Cypher Reliability & Agentic Hardening

> Goal: prove drevo's Cypher implementation is *production-ready under realistic agentic workloads* before exposing it to the world via Bolt (Phase 11). This is a **hard gate** between Phase 10 (executor) and Phase 11 (wire protocol): without parity diff vs Neo4j and a long-running agentic load test, official Neo4j drivers (`cypher-shell`, `neo4j-python-driver`, `neo4j-javascript-driver`) would silently receive *wrong* answers from drevo, with no signal at the wire level. Phase 10.5 closes that gap.
>
> The phase is structured around **five workload layers**, each measured independently so perf regressions can be bisected to the layer that introduced them. The Cypher layer specifically gives the honest "Cypher overhead vs raw Rust API" number — the answer to "is `executor` the bottleneck or the storage?".
>
> #### Agentic workload layers
>
> | # | Layer | Measures | Available when | Test home |
> |---|---|---|---|---|
> | 1 | **Rust API** (raw storage) | Upper bound of the storage layer alone. "What redb + our indexes can do, nothing on top." | **Today** | `tests/agentic_workload_rust_api.rs --ignored` |
> | 2 | **Cypher** (parse + execute) | **Executor overhead over the raw API.** Lexer + parser + AST walk + pattern matching cost. The honest answer to "how much do we lose by giving agents Cypher instead of Rust calls". | After `00063` (Phase 10 executor) | `tests/agentic_workload_cypher.rs --ignored` |
> | 3 | **Python API** (PyO3) | GIL release latency, serde_json Rust↔Python round-trip, GC pauses, `py.allow_threads` correctness. Sits *on top of* layer 1 or layer 2 — both `Drevo.query(cypher)` and `Drevo.bfs(...)` are valid client paths. | After `00115` (Phase 16 PyO3 bindings) | `tests/e2e/test_agentic_workload.py` (extended `00120`) |
> | 4 | **MCP stdio** (`drevo-mcp`) | Real Claude Code / Cline cost: stdio framing, JSON-RPC overhead, process boundary per session, tool-call serialisation. | After `00090` + `00121` (Phase 15 MCP server + Python-API tools) | `tests/mcp/agentic_workload.py` |
> | 5 | **Bolt wire** | PackStream + TLS round-trip cost — what `cypher-shell` actually measures across the network. | After Phase 11 (`00070`–`00074`) | `tests/bolt/agentic_workload.rs` |
>
> Each layer test runs the **same query mix** (70 % read, 20 % write, 10 % search) on the **same corpus** (10 k–100 k nodes), so the resulting "overhead per layer" graph is directly comparable. Hot/cold cache, p50/p95/p99 latency per query class, RSS + redb cache growth are recorded uniformly.
>
> #### Cross-cutting acceptance criteria
>
> - Every workload run completes a **30+ minute session** without OOM, deadlock, or RSS growth beyond a 20 % envelope.
> - **Nightly CI** runs an 8-hour soak of layer 1 + layer 2 — slow tests live behind `--ignored` / `pytest.mark.slow` so PR pipeline stays fast.
> - Parity diff vs Neo4j Community Edition 5.x reaches **≥ 95 %** on the curated 100-query corpus — the remaining ≤ 5 % are documented dialect divergences, not bugs.
> - Concurrency suite passes with **2 writers + 4 readers + 2 mixed agents** for 5 minutes.
> - Every PoC edge case in `00126` has an explicit test, not just an absence-of-crash assertion.

### Phase 11 — Bolt Protocol

> Goal: Neo4j-compatible wire protocol so existing official drivers (`cypher-shell`, `neo4j-python-driver`, `neo4j-javascript-driver`) connect without code changes. Requires Phase 10 — Bolt has nothing to execute without a working Cypher engine.

- [x] `00070` Bolt v4 wire protocol — `src/bolt/` ships the bytes-on-the-wire layer: PackStream codec ([`packstream`](src/bolt/packstream.rs)) covering Null / Boolean / Integer (TINY..INT_64) / Float / String / Bytes / List / Dictionary / Structure with deterministic key ordering; chunked message framing ([`chunked`](src/bolt/chunked.rs)) with 16-bit big-endian length prefixes, `0x0000` end-of-message terminator, and automatic split at the 65 535-byte cap; handshake parser + four-slot version negotiator ([`handshake`](src/bolt/handshake.rs)) — `MAGIC_PREAMBLE = 0x60 0x60 0xB0 0x17` enforced, supported versions are Bolt 4.4 and 4.3 in preference order; async TCP listener ([`listener`](src/bolt/listener.rs), `http` feature) that reads the handshake, replies with the negotiated version or `00 00 00 00`, and yields the still-open `TcpStream` to the next layer. Errors live in their own [`BoltError`](src/bolt/error.rs) so unrelated modules (FFI, WASM, HTTP) don't have to match on Bolt-specific variants. **Not in scope:** session loop (HELLO / RUN / PULL / DISCARD / RESET / GOODBYE) — that lands with `00071` on top of this foundation. Tests: 24 unit (inline `#[cfg(test)] mod tests`) + 66 integration tests across `tests/bolt_packstream_tests.rs` (45 cases — every marker family, byte-for-byte pinned), `tests/bolt_chunked_tests.rs` (9 — small / max-size / multi-chunk / truncated / back-to-back), `tests/bolt_handshake_tests.rs` (9 — magic / four-slot extraction / preference order / unsupported), `tests/bolt_listener_tests.rs` (3 — real `tokio::net::TcpListener` loopback with successful 4.4 negotiation, all-unsupported reply, bad-magic refusal).
- [x] `00071` Bolt session — `src/bolt/session.rs` ships the per-connection state machine that official Neo4j drivers expect after the handshake: `Connected → Ready → Streaming → Ready` plus `Failed` (cleared only by `RESET`) and `Defunct` (after `GOODBYE`). Six client message families are decoded from PackStream `Structure` (`HELLO 0x01`, `GOODBYE 0x02`, `RESET 0x0F`, `RUN 0x10`, `DISCARD 0x2F`, `PULL 0x3F`) plus `BEGIN/COMMIT/ROLLBACK` (`0x11/0x12/0x13`) which decode successfully but respond `FAILURE { message: "lands with task 00072" }` so a tx-aware driver gets a deterministic answer instead of a torn connection. Server replies (`SUCCESS 0x70`, `RECORD 0x71`, `IGNORED 0x7E`, `FAILURE 0x7F`) are encoded back via the same codec. RUN parses through [`cypher::parser::parse`](src/cypher/parser.rs) and executes through [`cypher::executor::execute`](src/cypher/executor.rs); the materialised `ExecResult` rows are stashed and drained by `PULL { n }` (emits up to `n` `RECORD`s + trailing `SUCCESS { has_more, type }`) or `DISCARD { n }` (drops without emitting). Cypher errors are mapped to Neo4j status codes (`Neo.ClientError.Statement.SyntaxError` for parse errors, `…SemanticError` for unbound vars / type mismatches / invalid mutations, `…ParameterMissing` for `$name` gaps, `Neo.DatabaseError.…` for storage / unsupported). PackStream parameters round-trip into Cypher values; returned `Node` rows are encoded as Bolt v4 `Structure { tag: 0x4E, fields: [id, labels, properties] }`, `Relationship` as `tag: 0x52`. [`run_session_sync`](src/bolt/session.rs) drives the loop over any `Read + Write` pair; [`accept_and_run_session`](src/bolt/listener.rs) bundles handshake + async session loop in a single call for `tokio::spawn`-per-connection servers. Tests: 10 inline unit + 37 integration in `tests/bolt_session_tests.rs` (tag-byte pins, decode/encode coverage, every state transition, parameter conversion, syntax-error path, Node-structure round-trip, full sync HELLO→RUN→PULL→GOODBYE driver) + 2 new async listener tests in `tests/bolt_listener_tests.rs` exercising real TCP. **Not in scope (deferred):** BEGIN/COMMIT/ROLLBACK (`00072`), TLS (`00073`), authentication (`00074`).
- [x] `00072` Bolt transaction integration — `src/bolt/session.rs` extends the `00071` state machine with `TxReady` / `TxStreaming` and wires the `BEGIN (0x11)` / `COMMIT (0x12)` / `ROLLBACK (0x13)` messages onto a fresh undo-log journal in [`Drevo::tx_begin`](src/db.rs) / [`tx_commit`](src/db.rs) / [`tx_rollback`](src/db.rs). The journal captures the inverse of every mutation method (`create_node`, `update_node`, `delete_node`, `create_edge`, `update_edge`, `delete_edge`) and `tx_rollback` replays the captured ops in reverse order so a `CREATE`/`UPDATE`/`DELETE` chain inside a tx unwinds to the pre-`BEGIN` state — including cascade-deleted edges restored by their own journaled ops. State transitions: `Ready -[BEGIN]-> TxReady -[RUN]-> TxStreaming -[PULL/DISCARD drained]-> TxReady -[COMMIT|ROLLBACK]-> Ready`. `RESET` and `GOODBYE` issued inside an open tx roll it back before transitioning so the next session isn't left holding the journal slot. A second concurrent `BEGIN` against the same `Drevo` handle gets `Neo.TransientError.Transaction.Outdated` — MVP is single-writer; proper multi-tx isolation lands with MVCC (`00080`–`00084`). Tests: 10 inline unit tests on `Drevo::tx_*` + 13 new session-layer tests in `tests/bolt_session_tests.rs` (state-machine pins for every new transition, rollback-undoes-CREATE/UPDATE/DETACH-DELETE, RESET-during-tx rollback, GOODBYE-rollback for next-session BEGIN, nested-BEGIN failure, fail-inside-tx routing) + 1 new TCP-loopback test in `tests/bolt_listener_tests.rs` driving `BEGIN → RUN(CREATE) → PULL → COMMIT → RUN(MATCH) → PULL → GOODBYE` over real TCP. **Not in scope:** TLS (`00073`), authentication (`00074`).
- [x] `00073` TLS for Bolt — `src/bolt/tls.rs` (feature `bolt-tls`) ships [`TlsConfig::from_pem`](src/bolt/tls.rs) / [`TlsConfig::from_pem_files`](src/bolt/tls.rs) (cert chain + PKCS#8 / PKCS#1 / SEC1 key parsing via [`rustls-pemfile`](https://crates.io/crates/rustls-pemfile)), plus [`accept_handshake_tls`](src/bolt/tls.rs) and [`accept_and_run_session_tls`](src/bolt/tls.rs) — drop-in `_tls` siblings of the plain-TCP entry points from `00070`/`00071`. The async TCP listener was first refactored to a generic [`accept_handshake_on<S>`](src/bolt/listener.rs) / [`run_session_on<S>`](src/bolt/listener.rs) shape over any `AsyncRead + AsyncWrite + Unpin` stream, so the plain-TCP and TLS code paths share the same session-loop bytes — TLS adds only the [`tokio_rustls::TlsAcceptor`](https://docs.rs/tokio-rustls) wrap around the existing handshake + session loop, plus a new [`BoltError::Tls(String)`](src/bolt/error.rs) variant (kept as a `String` payload so the rest of the Bolt module compiles whether or not the feature is enabled). Crypto provider is `ring` — pure Rust, no C toolchain required on the build host. The `bolt-tls` Cargo feature implies `http`; default builds and every existing CI gate keep their dep graph unchanged (verified by `cargo build --no-default-features --features redb-backend,http,cbindgen` still green). Tests: 6 inline unit tests in `src/bolt/tls.rs` (empty / malformed / missing PEM, happy-path self-signed PKCS#8, from-disk PEM read, missing-file → `BoltError::Io`) + 3 integration tests in `tests/bolt_tls_tests.rs` (TLS handshake + Bolt 4.4 negotiation over `tokio_rustls`; full HELLO → RUN → PULL → GOODBYE over TLS; plain-TCP client against a TLS listener gets rejected). CI gates: `ci.yml` `test` job adds a dedicated nextest step `cargo nextest run --features bolt-tls -E 'binary(bolt_tls_tests) | (kind(lib) & test(bolt::tls))'` (~9 extra tests) and `clippy` job adds `cargo clippy --all-targets --features bolt-tls -- -D warnings`.
- [x] `00074` Authentication — `src/bolt/auth.rs` ships the auth layer Neo4j drivers expect inside `HELLO`. Two halves, split along the dependency line: the [`Authenticator`](src/bolt/auth.rs) trait + [`AuthOutcome`](src/bolt/auth.rs) are **dependency-free and always compiled**, so the session state machine holds an `Option<&dyn Authenticator>` (default builds gain the wiring with zero new deps and can plug in their own backend — LDAP, a callback, a test double); the concrete [`UserStore`](src/bolt/auth.rs) — basic auth + session tokens + user table — sits behind the new `bolt-auth` Cargo feature (pulls `argon2`). **Basic auth:** `HELLO { scheme: "basic", principal, credentials }` is verified against the user table, whose entries are Argon2id PHC strings (per-user random salt — two users with the same password get different stored hashes; never plaintext or an unsalted digest). **Session tokens:** [`UserStore::issue_token`](src/bolt/auth.rs) mints an opaque 256-bit bearer token after a successful login; `HELLO { scheme: "bearer", credentials: <token> }` re-authenticates without resending the password, and [`revoke_token`](src/bolt/auth.rs) is the logoff path. Transport-agnostic drivers: [`run_session_sync_with_auth`](src/bolt/session.rs) (plain `std::io`) + the async [`accept_and_run_session_with_auth`](src/bolt/listener.rs) / [`run_session_on_with_auth`](src/bolt/listener.rs) (feature `http`, works over both plain TCP and TLS via the generic stream shape from `00073`). Tests: 12 inline unit (UserStore basic verify / unknown user / duplicate-user reject / salted-hash guard / bearer round-trip + revoke + uniqueness / unsupported-scheme deny — gated `bolt-auth`) + 4 dependency-free session-layer tests in `tests/bolt_session_tests.rs` (a `FixedCreds` mock authenticator proving the session enforces *any* `Authenticator`: no-auth accepts, valid creds → `Ready`, bad creds → `Defunct` + `Unauthorized`, full `run_session_sync_with_auth` rejects-then-closes with the queued `CREATE` never running) + 4 `bolt-auth`-gated end-to-end tests in `tests/bolt_auth_tests.rs` (real `UserStore` through the sync driver: valid basic auth runs `RETURN`, wrong password blocks a queued `CREATE`, unknown user denied, issued bearer token authenticates). CI gates: `ci.yml` `test` job adds a `bolt-auth` nextest step (`-E 'binary(bolt_auth_tests) | (kind(lib) & test(bolt::auth))'`) and `clippy` job adds `cargo clippy --all-targets --features bolt-auth -- -D warnings`.

### Phase 12 — Vector Storage & Search

> Goal: native graph + vector hybrid queries (traverse AND similarity in one query) — enables RAG and semantic search over the knowledge graph. Independent of Phase 11; can run in parallel with Bolt work.

- [x] `00075` Vector value type + distance functions — `src/vector/` ships the dependency-free, always-compiled foundation the rest of Phase 12 sits on. [`Vector`](src/vector/mod.rs) is a validated newtype over `Vec<f32>` with [`from_json_value`](src/vector/mod.rs) / [`to_json_value`](src/vector/mod.rs) — embeddings live inside node `properties` as arbitrary [`serde_json::Value`], so the conversion validates every element is a finite number **once at the boundary** (non-array → `NotAnArray`, non-number element → `NonNumeric`, NaN/±∞ → `NonFinite`) and hands back a `Vector` the math can trust; `Deref<Target = [f32]>` lets a `&Vector` flow straight into the distance functions with no copy. [`distance`](src/vector/distance.rs) provides the three measures over plain `&[f32]`: [`dot_product`](src/vector/distance.rs) (`Σ aᵢ·bᵢ`), [`cosine_similarity`](src/vector/distance.rs) (`(a·b)/(‖a‖·‖b‖) ∈ [-1,1]`, the relevance score `00077`'s `similar(...)` predicate ranks on), and [`euclidean_distance`](src/vector/distance.rs) (`√Σ (aᵢ−bᵢ)²`). All three reject a dimension mismatch (`DimensionMismatch { left, right }`), an empty input (`Empty`), or — for cosine — a zero-magnitude operand (`ZeroVector`) with a recoverable [`VectorError`](src/vector/mod.rs) instead of panicking, because the inputs originate from user-supplied JSON and a length error there must surface across the FFI / Bolt boundary, not crash. **SIMD acceleration** (`std::simd` is nightly-only; this crate is stable-pinned) is delivered without a new dependency by writing the hot loops with eight independent lane accumulators over `chunks_exact(8)` plus a scalar remainder — the shape LLVM's auto-vectorizer needs to emit packed `addps`/`fmla` (a single `f32` accumulator forces a serial FP dependency chain the optimizer can't reorder). **Not in scope:** the HNSW index (`00076`), the Cypher `similar(...)` predicate (`00077`), and redb persistence (`00078`) build on top of this. Tests: 16 inline unit (10 in `distance` — dot/cosine/euclidean correctness incl. orthogonal/opposite, lane-boundary spanning, zero-vector + dimension-mismatch + empty errors; 6 in `mod` — JSON parse / round-trip / non-array / non-numeric rejection / Deref-into-distance) + 11 integration in `tests/vector_distance_tests.rs` (cosine ranking, hand-computed agreement, 100- & 384-dim embeddings crossing the lane boundary, JSON round-trip, integer-element parse, malformed-JSON recovery, mismatch / zero / empty across all three measures).
- [x] `00076` HNSW vector index — built on top of redb adjacency storage. Shipped in PR #116 (commit `6c428b0`); checkbox corrected here after it was left unticked on merge.
- [x] `00077` Joint graph+vector queries — `MATCH (n) WHERE similar(n.embedding, $q, 0.85) RETURN n` (Cypher extension). The executor gains its **first scalar (non-aggregation) function**, `similar(vector, query, threshold)`, which returns `true` when the [`cosine_similarity`](src/vector/distance.rs) between its first two arguments is at least `threshold`. Embeddings live inside node `properties` as JSON arrays, so they reach the evaluator as `Value::List` of numbers — [`similar_operand`](src/cypher/executor.rs) converts each operand into a dense `Vec<f32>` (accepting both integer and float elements) before handing it to the `00075` distance function, and the cosine score is compared against the threshold with an **inclusive** `>=` (a vector vs itself scores exactly `1.0` and must pass `threshold = 1.0`). Because `similar(...)` is just an expression, it composes everywhere WHERE / RETURN expressions already work: `WHERE similar(...) AND n.status = 'public'`, mixed with traversal (`MATCH (a)-[:cites]->(b) WHERE similar(a.embedding, $q, 0.9)` — the canonical graph-RAG idiom that expands a similarity hit into its neighbourhood), or projected directly (`RETURN similar(...) AS hit`). **NULL propagation** is the key correctness choice: a node that simply lacks the embedding property evaluates the predicate to `NULL` (falsy under WHERE) rather than erroring, so a similarity filter can scan a heterogeneous label without every vector-less node aborting the query; genuine data errors — wrong arity, a non-list / non-numeric operand, a dimension mismatch between the stored and query vectors, or a zero-magnitude operand (cosine is undefined) — surface as the new recoverable [`ExecError::InvalidFunctionCall`](src/cypher/executor.rs) (mapped to a Bolt `SEMANTIC_ERROR`). Implementation threads through the executor's **upfront strict validator** (`validate_expr_supported` / `validate_expr_supported_in_projection`): a new `is_scalar_function_name` whitelist lets `similar` past the "no function calls yet" gate while every other name still gets the deterministic `Unsupported` pointer — so the change is purely additive on top of `00063`–`00069` and `00075`. Tests: 5 inline unit (case-insensitive name match incl. dotted-name rejection, `similar_operand` int/float acceptance + non-list / non-numeric rejection, end-to-end zero-magnitude error) + 18 integration in `tests/cypher_similar_tests.rs` (identical / orthogonal / opposite / magnitude-invariant cosine, inclusive threshold boundary, negative threshold, inline-list and `$param` query vectors, RETURN projection, NULL-propagation in both WHERE and RETURN, the four error classes, unknown-function still-unsupported, and CBT-journal + graph-RAG + compound-predicate scenarios). The HNSW index (`00076`) is the acceleration path; this predicate is the brute-force-correct semantics it must match — joining them under a planner is `00078`+ work.
- [x] `00078` Vector persistence — redb tables, batch insert API. The `00075` [`Vector`](src/vector/mod.rs) type and the `00076` [`HnswIndex`](src/vector/hnsw.rs) both live purely in memory; this task gives embeddings a durable home so they survive a process restart, and the batched-write path that makes bulk ingest viable. [`vector::store`](src/vector/store.rs) is a free-function layer (mirroring [`fts::index`](src/fts/index.rs)) over the existing [`StorageBackend`](src/storage/backend.rs): an embedding is a sidecar column keyed by node id under a `vec:{node_id_le8}` → `bincode(Vector)` schema — looked up in O(log N), scanned as one contiguous prefix range, and serialized via the new `serde` derives on `Vector` (transparent, so the on-disk form is the bare `Vec<f32>` with no extra framing). The **batch insert API** ([`store::put_batch`](src/vector/store.rs), surfaced as [`Drevo::set_embeddings_batch`](src/db.rs)) is the headline: a whole corpus is embedded at once, but per-`put` redb transactions `fsync` on every row, so the store folds the slice into a single [`StorageBackend::put_batch`](src/storage/backend.rs) — a **new trait method** that defaults to a `put` loop but is overridden by [`RedbBackend`](src/storage/redb.rs) to commit the entire batch in one `begin_write`/`commit` (all-or-nothing) and by [`MemoryBackend`](src/storage/memory.rs) to take its lock once. The [`Drevo`](src/db.rs) facade adds `set_embedding` / `get_embedding` / `delete_embedding` / `embedding_count` / `set_embeddings_batch` (the mutating entry points validate the owning node exists, returning [`DrevoError::NodeNotFound`](src/error.rs) before any write so a batch is rejected as a unit), and `delete_node` now **cascade-deletes** the embedding sidecar so the store never accumulates orphans. The persistence → query-acceleration bridge is [`store::build_hnsw`](src/vector/store.rs) / [`Drevo::build_vector_index`](src/db.rs): the in-memory HNSW graph (`00076`) is reconstructed after a reopen by replaying the durable vectors through [`HnswIndex::insert`](src/vector/hnsw.rs) in node-id order — the approximate-nearest-neighbour acceleration path for which the brute-force `00077` `similar(...)` predicate is the correctness baseline. A new recoverable [`DrevoError::Vector`](src/error.rs) (`#[from] VectorError`, mapped to HTTP 400 / Bolt `SEMANTIC_ERROR` / Python `ValueError`) surfaces a dimension mismatch encountered while rebuilding the index. **Not in scope:** rewiring the `similar(...)` executor to consult the index (the brute-force scan stays the semantics baseline), and making embedding persistence transaction-aware (an MVCC / `00080`+ concern — the cascade delete is intentionally not undo-logged). Tests: 14 inline unit in `src/vector/store.rs` (key round-trip, malformed-key rejection, put/get/delete/overwrite, count, batch insert + empty-batch no-op, node-id-ordered scan, HNSW rebuild incl. empty-store and dimension-mismatch surfacing) + 15 integration in `tests/vector_persistence_tests.rs` (Memory ⨉ Redb backend parity for every store function, `vec:` prefix isolation from `node:`/`edge:` rows, redb reopen durability, post-reopen HNSW nearest-neighbour query, facade node-existence validation, cascade-on-`delete_node`, batch all-or-nothing on a bad id, facade index round-trip, and an end-to-end graph-RAG corpus that persists → reopens → rebuilds → retrieves a similarity hit and expands it into its `cites` neighbourhood).
- [x] `00079` Embedding integration helpers — callable from Python SDK / FastMCP. The Phase 12 capstone: it surfaces the Rust vector engine (`00076` HNSW + `00078` durable store) to Python and adds the ergonomic helpers the SDK and a FastMCP server call. **PyO3 bridge** ([`drevo-py/src/handle.rs`](drevo-py/src/handle.rs)) — six new `Drevo` methods mirroring the Rust facade, each releasing the GIL: `set_embedding(node_id, list[float])`, `set_embeddings_batch(list[tuple[int, list[float]]])` (one transaction on redb), `get_embedding`, `delete_embedding`, `embedding_count`, and `vector_search(query, k) -> list[tuple[int, float]]` (rebuilds the HNSW index from the durable store and returns nearest-first `(node_id, distance)`; a dimension mismatch maps to `ValueError` via the `00078` [`DrevoError::Vector`](src/error.rs)). **Pure-Python helpers** ([`drevo/rag/embedding.py`](drevo-py/python/drevo/rag/embedding.py), the `drevo.rag` "no-FFI, pytest-only" layer) — the `Embedder` protocol (the structural `list[str] -> list[list[float]]` shape every framework's embedder satisfies), the `VectorHit` frozen dataclass (`node` + raw `distance` + clamped `similarity`), `embed_and_store(drevo, nodes, embedder)` (embeds each node's `text` property or title, persists in one batch), and `vector_search(drevo, query, *, embedder=None, k=10)` (raw-vector or `str` query → ranked `VectorHit`s resolved back to `Node`s). Tests: 8 Rust scaffolding (`tests/python_embedding_helpers_tests.rs`, the shape gate for Rust-only runners) + 28 pytest — `tests/unit/test_vector_bridge.py` (10: round-trip, missing-node validation, batch all-or-nothing, cascade-on-delete, nearest-first search, dimension-mismatch `ValueError`), `tests/unit/test_rag_embedding.py` (15: `Embedder` protocol, `embed_and_store` text-selection + size-mismatch, `vector_search` raw/str/empty/k-guard, `ingest` first-class persistence, `retrieve_with_embedding` seed+expand) and `tests/integration/test_vector_embeddings.py` (5: redb reopen durability, post-reopen search, on-disk ingest+retrieve, graph-RAG retrieve-with-embedding). **This completes Phase 12** (`00075`–`00079`).

### Phase 13 — Concurrency & MVCC

> Goal: production-grade concurrent reads and writes. Today drevo uses single-writer locking; this phase introduces MVCC so readers never block writers. Highest-risk phase — touches every storage path.

- [x] `00080` Read-write separation — `RwLock` replacing `Mutex`, concurrent redb read transactions. Phase 13 opens by lifting the in-memory backend's read bottleneck: [`MemoryBackend`](src/storage/memory.rs) now holds its `BTreeMap` behind a [`std::sync::RwLock`] instead of a `Mutex`, so [`get`](src/storage/memory.rs) / [`scan_prefix`](src/storage/memory.rs) (and the snapshot read inside [`flush`](src/storage/memory.rs)) take a **shared** read lock while [`put`](src/storage/memory.rs) / `put_batch` / [`delete`](src/storage/memory.rs) take an **exclusive** write lock — any number of readers now run in parallel where they previously serialised one-at-a-time. The redb backend already had concurrent reads for free (each [`begin_read`](src/storage/redb.rs) opens an independent MVCC snapshot); this task adds the integration coverage that **pins** that property (`tests/read_write_separation_tests.rs` holds 8 redb read transactions open across a `Barrier` and interleaves a writer with 6 readers). A bonus reliability win falls out of the std semantics: an `RwLock` only poisons on a *write*-mode panic, so a panicking read query can no longer take the whole backend down — pinned by `reader_panic_does_not_poison`. Both `get`/`scan_prefix`/`flush` map `RwLock::read`/`write` poison to the existing [`StorageError::LockPoisoned`](src/storage/error.rs), so the error contract is unchanged. **Not in scope:** tuple-versioning, transaction snapshots, and write-write conflict handling — those are MVCC proper (`00081`+). Tests: 7 new inline unit (concurrent-readers-share-the-lock, writer-excludes-readers, 100-key 16-thread read storm, reader-panic-no-poison, plus the two renamed poison-mapping tests) + 6 integration in `tests/read_write_separation_tests.rs` (16-thread shared-`Drevo` read storm, writer-vs-8-readers consistency, concurrent title+uuid lookup, and the three redb concurrency tests). WASM still compiles (`RwLock` is available on `wasm32-unknown-unknown`, same as `Mutex`).
- [x] `00081` MVCC — tuple versioning (xmin/xmax), transaction snapshots, visibility checks. The new dependency-free, always-compiled [`mvcc`](src/mvcc/mod.rs) module is the visibility core the rest of Phase 13 builds on — modelled on PostgreSQL's `(xmin, xmax, snapshot)` design in three cooperating pieces. [`TransactionManager`](src/mvcc/transaction.rs) allocates monotonic [`Xid`](src/mvcc/transaction.rs)s (`1, 2, …`; `0` is the reserved [`INVALID_XID`](src/mvcc/transaction.rs) sentinel), keeps a commit log mapping each id to its [`XidStatus`](src/mvcc/transaction.rs) (`InProgress` / `Committed` / `Aborted`), and captures point-in-time [`Snapshot`](src/mvcc/transaction.rs)s — the `(xmin, xmax, active-set)` triple where `xmin` is the lowest still-active id, `xmax` is the next id to be allocated, and `active` is the set in progress at capture time. [`Version`](src/mvcc/version.rs) is an immutable value stamped with the `xmin` that **created** it and the `xmax` that **retired** it (`INVALID_XID` while live); storage is append-only — nothing is mutated in place. [`VersionedStore`](src/mvcc/store.rs) is the key → version-chain map: [`put`](src/mvcc/store.rs) retires the current live version (stamps its `xmax`) and appends a fresh one, [`delete`](src/mvcc/store.rs) only stamps the `xmax`, and [`get`](src/mvcc/store.rs) walks the chain newest-first returning the first version visible to a snapshot. Everything reduces to one predicate — `visible(v, snap) = snap.sees_effect(v.xmin) && !snap.sees_effect(v.xmax)` — where an effect is visible iff it is the snapshot's own transaction, or it had committed before the snapshot and was not still active at that moment. A transaction captured as active stays invisible to that snapshot **forever** (even after it commits later), which is what gives repeatable reads: an older reader keeps seeing the world as of its snapshot while writers move on, so readers and writers never observe each other's in-flight state. Lock poison surfaces as the recoverable [`MvccError::LockPoisoned`](src/mvcc/error.rs) rather than propagating a panic. **Not in scope:** reclaiming dead versions below the oldest live `xmin` horizon (GC, `00082`), detecting two writers retiring the same live version as a write-write conflict (OCC, `00083`), and choosing per-statement vs per-transaction snapshots (isolation levels, `00084`) — all build directly on these primitives. The store is the logical visibility engine; lock-free physical reads are a later performance concern. Always compiled; WASM-safe (no new deps, `std::sync` only).
- [x] `00082` Garbage collection — vacuum dead tuple versions, background GC thread. Append-only MVCC storage (`00081`) means every update leaves a dead version behind forever; this task reclaims them without ever pulling a version a live reader can still see. The horizon machinery lands on [`TransactionManager`](src/mvcc/transaction.rs): [`begin_snapshot`](src/mvcc/transaction.rs) captures a snapshot *and* publishes its `xmin` into a reference-counted `active_snaps` multiset, handing back an RAII [`SnapshotGuard`](src/mvcc/transaction.rs) (receiver `self: &Arc<Self>`, so the guard owns a manager handle and is `Send + 'static` — movable into reader threads) that withdraws the `xmin` on drop; the smallest registered `xmin` is the [`gc_horizon`](src/mvcc/transaction.rs) (or the next id when no readers are registered). Plain [`snapshot`](src/mvcc/transaction.rs)s stay untracked — one-shot reads the collector need not respect — so the visibility core is unchanged. The reclamation predicate is [`Version::is_reclaimable`](src/mvcc/version.rs): a version is collectable below a horizon iff it was **superseded/deleted by a committed transaction** `xmax < horizon` (every respected snapshot sees the deletion, since `xmax < horizon <= snapshot.xmin`) **or created by an aborted transaction** `xmin < horizon` (dead on arrival); live versions and those retired by an in-progress or aborted deleter are always kept. [`VersionedStore::vacuum`](src/mvcc/store.rs) filters every chain through it under the existing write lock, drops emptied chains from the index entirely (no tombstone leak), preserves surviving order, and returns a [`VacuumReport`](src/mvcc/store.rs) (`reclaimed_versions` / `emptied_keys`); [`vacuum_to_horizon`](src/mvcc/store.rs) is the convenience that vacuums at the shared manager's live horizon. The policy layer is [`GcWorker`](src/mvcc/gc.rs): a background thread that vacuums on a configurable cadence, exposes `reclaimed_total` / `cycles` for observability, and shuts down promptly and deterministically — `stop()` (and `Drop`) flip a `Mutex<bool>` and signal a [`Condvar`](https://doc.rust-lang.org/std/sync/struct.Condvar.html) so the thread wakes from its interval wait at once, then joins. Lock order is strictly store→manager (vacuum holds the store write lock, then reads the commit log), so it cannot deadlock with readers/writers. The worker spawns an OS thread and is gated `#[cfg(not(target_arch = "wasm32"))]`; the pure vacuum mechanism stays available everywhere so a WASM host collects manually. **Not in scope:** write-write conflict detection (OCC, `00083`), isolation levels (`00084`), pruning the commit-log `status` map itself, and wiring GC into the `Drevo` storage backend (MVCC is still a standalone engine until `00083`/`00084`). - [x] `00083` Optimistic concurrency control — write-write conflict detection, retry semantics. Append-only versioning (`00081`) by itself does nothing to stop two concurrent transactions from each retiring the *same* live version and silently losing one update; this task adds first-updater-wins conflict detection plus the retry loop that turns a detected conflict into forward progress. **Detection** lands as the conflict-checked twins [`VersionedStore::put_checked`](src/mvcc/store.rs) / [`delete_checked`](src/mvcc/store.rs): both take the writer's `Snapshot`, run the check, and mutate under a **single** store write-lock acquisition (no time-of-check/time-of-use gap — two threads cannot both pass the check then both append). The check reduces to one observation — only the **chain head** can carry a concurrent modification, since a serial update retires the previous live version and appends a fresh one, so whoever last touched the key authored the head. The "deciding" transaction is the head's `xmin` when the head is live (a concurrent insert/update) or its `xmax` when the head is a tombstone (a concurrent delete); it **conflicts** iff it is a different, still-in-flight effect — not the writer itself, not [`INVALID_XID`](src/mvcc/transaction.rs), not already visible to the writer's snapshot (a commit that landed *before* the snapshot is the row the writer legitimately builds on, not a race), and not aborted (an aborted mark is void). What survives all four filters is exactly an in-progress writer or one that committed *after* the writer's snapshot — the loser is refused with [`MvccError::WriteConflict { conflicting }`](src/mvcc/error.rs) and the store is left byte-for-byte untouched. **Retry** is [`run_with_retry`](src/mvcc/occ.rs): it begins a transaction, captures a fresh snapshot, runs a closure `FnMut(Xid, &Snapshot) -> Result<T>`, and on `Ok` commits / on `WriteConflict` aborts and replays against a brand-new snapshot (which now observes the winner's commit, so the next attempt re-derives its change rather than colliding again) / on any other error aborts and propagates unchanged; after `max_retries` extra attempts it gives up with [`MvccError::RetriesExhausted { attempts }`](src/mvcc/error.rs) (`max_retries == 0` ⇒ exactly one try). Lock order is unchanged (store write-lock → manager read-lock, matching the GC vacuum), so OCC cannot deadlock with readers/writers/the collector. **Not in scope:** per-statement vs per-transaction snapshot selection and the configurable Read Committed / Snapshot Isolation / Serializable levels (`00084`), and wiring the engine into the [`Drevo`](src/db.rs) mutation paths — the MVCC module stays standalone until `00084`, exactly as `00081`/`00082` left it. Tests: 17 inline unit (10 in `store` — fresh-key put, serial no-conflict, conflict vs committed winner, conflict vs in-progress writer, store-untouched-after-conflict, self-update allowed, aborted-concurrent-writer ignored, delete detects concurrent update, delete-then-update conflict, missing-key delete; 7 in `occ` — success commits, single-run when clean, non-conflict error propagates+aborts, retries until clean, exhausted budget count, zero-retries-once, each-retry-observes-the-winner lost-update guard) + 8 integration in `tests/mvcc_occ_tests.rs` (bug-tracker two-triager status race, task-manager assignment retry respecting the first assignee, ERP 8-terminal × 25-sale concurrent stock decrement that loses no sale, CBT-journal stale-edit-rejected-then-retried, delete-then-concurrent-update conflict, exhausted-budget reporting, a 12-thread × 40-increment storm whose counter must equal every increment, and a `proptest` proving N conflict-checked increments through `run_with_retry` always converge to exactly N). 2424 → 2449 nextest (+25). Always-compiled core; WASM-safe (no new deps, `std::sync` only).
- [x] `00084` Isolation levels — Read Committed, Snapshot Isolation, Serializable (configurable). The MVCC primitives (`00081`–`00083`) give exactly one behaviour — snapshot isolation — so this task adds the [`isolation`](src/mvcc/isolation.rs) module that turns it into three configurable [`IsolationLevel`](src/mvcc/isolation.rs)s by controlling **when** a transaction's read snapshot is captured and **what** is validated at commit. A [`Transaction`](src/mvcc/isolation.rs) is an RAII handle over a [`VersionedStore`](src/mvcc/store.rs) (begun via [`begin_transaction`](src/mvcc/isolation.rs)): [`ReadCommitted`](src/mvcc/isolation.rs) re-snapshots before every statement (non-repeatable reads, always latest committed — never a dirty read); [`SnapshotIsolation`](src/mvcc/isolation.rs) (a.k.a. Repeatable Read) holds one snapshot for the transaction's life (a stable, repeatable view, but permits write-skew); [`Serializable`](src/mvcc/isolation.rs) adds commit-time **read-set validation** — it records every key read and, at commit, refuses with [`MvccError::SerializationFailure`](src/mvcc/error.rs) if any of them was modified by a transaction that *committed* after its snapshot (first-committer-wins), closing the write-skew gap. Validation is committed-only (an in-flight racer never aborts the first committer) and the validate-then-commit runs under a single store write-lock acquisition so two serializable transactions can never both pass and both commit; lock order stays store→manager (no deadlock with readers/writers/GC). Write-write conflict detection (`00083`) is always on at every level. Dropping an unfinished `Transaction` aborts it, so none ever lingers in-progress. [`run_transaction`](src/mvcc/isolation.rs) is the isolation-aware retry loop (sibling of [`run_with_retry`](src/mvcc/occ.rs), which now also retries `SerializationFailure`). **Not in scope:** predicate/phantom anomalies over range scans (the read set tracks individually-read keys, not predicates), and wiring the standalone engine into the [`Drevo`](src/db.rs) redb-backed mutation paths — the MVCC module stays self-contained as it has since `00081`. Tests: 18 inline unit (level predicates/defaults, begin/commit/abort/drop-aborts, SI repeatable reads, RC sees-committed/no-dirty-read, write-write rejection, serializable write-skew prevention + disjoint-read-sets + read-only-never-fails + first-committer-not-aborted-by-in-flight, and four `run_transaction` cases) + 8 integration in `tests/mvcc_isolation_tests.rs` (RC dashboard committed-not-dirty, SI ERP month-end stable report, SI permits write-skew vs Serializable refuses it keeping the on-call invariant, serializable disjoint CBT journals both commit, an 8-thread × 25 serializable contended counter that converges via retry, a 16-reader mixed-level no-tear storm, and a `proptest` proving serializable increments converge to the exact sum). 2449 → 2475 nextest (+26). Always-compiled core; WASM-safe (no new deps, `std::sync` only).

- [x] `00089` Memory budget & backpressure — closes Phase 14 by turning the planner's row estimates into a guard against running out of memory on a large graph. New always-compiled, dependency-free [`planner::budget`](src/planner/budget.rs) submodule (atomics + `std` only, WASM-safe, no spawned threads), three cooperating pieces in the same standalone-engine discipline `00085`–`00088` kept — read estimates + parsed plans, **not yet wired into the executor**. **OOM guard:** [`MemoryBudget`](src/planner/budget.rs) is a lock-free, clonable byte accountant; a producer calls [`try_reserve`](src/planner/budget.rs) before buffering rows and gets back either an RAII [`MemoryReservation`](src/planner/budget.rs) that releases its bytes on drop (`Send + 'static`, so it moves into a worker thread alongside the work it accounts for) or a recoverable [`BudgetError::MemoryBudgetExceeded`](src/planner/budget.rs) — a query that would blow the cap **fails cleanly instead of exhausting process memory**. Reservation is a compare-and-swap loop on a shared `AtomicUsize`, so concurrent reservers can never jointly overshoot the ceiling (the CAS loser re-reads the new total and re-checks); a `peak()` high-water mark is tracked for observability and `unlimited()` models a `usize::MAX` ceiling. **Memory-limited query execution:** [`estimate_peak_memory`](src/planner/budget.rs) sums the working set of every *blocking* operator across a planned [`PlanNode`](src/planner/plan.rs) tree — a `DISTINCT` [`Projection`](src/planner/plan.rs) holds its whole deduplicated output, a [`CartesianProduct`](src/planner/plan.rs) buffers its smaller build side, while the pipelined operators (scans, expands, filters, `SKIP`/`LIMIT`, plain projection) stream at `O(1)` rows — and [`MemoryBudget::admits`](src/planner/budget.rs) refuses a plan whose estimated peak passes the ceiling **before a single row is read** (a fully streaming plan fits any budget). The estimate is deliberately a conservative upper bound (it sums concurrent materialisations) and saturates rather than overflowing on a pathological cartesian blow-up. **Backpressure:** [`Backpressure`](src/planner/budget.rs) is a high/low-watermark throttle with hysteresis — [`observe`](src/planner/budget.rs) emits `Pause` the first time usage reaches the high mark and stays paused until usage falls to or below the low mark, when it emits `Resume` once, so a streaming producer never oscillates on a single threshold; [`from_budget`](src/planner/budget.rs) derives the marks from a fraction of a budget's ceiling. A coarse [`DEFAULT_ROW_WIDTH_BYTES`](src/planner/budget.rs) (`64`) joins the planner's documented `DEFAULT_*` constants for callers without a measured projection width. Evaluation is **deny-overrides and closed-world**: a matching `Deny` refuses even when an `Allow` also matches (so a broad grant can be carved out by a narrow denial — "read every node *except* `SealedRecord`"), and with no matching permission the request is denied by default. Inheritance resolution is **cycle-safe** (a visited set breaks `a→b→a` loops so evaluation always terminates) and tolerant of unknown parents; the opt-in [`validate`](src/authz/policy.rs) reports dangling-parent (`UnknownRole`) and cycle (`RoleCycle`) defects up front for callers that prefer to fail at configuration time. A *subject* is any opaque identity string — exactly the username the Bolt [`UserStore`](src/bolt/auth.rs) resolves from a session token. Keeps its own [`AuthzError`](src/authz/policy.rs) channel rather than touching the crate-wide `DrevoError`; like the planner (`00085`–`00089`) and MVCC (`00081`) engines in their early tasks, this is the policy substrate — **not yet wired into the executor / HTTP API / Bolt session** (enforcing a decision at each request boundary is later-task work). - [x] `00095` Replication MAIN/REPLICA — a production graph database rarely runs as a single process: writes funnel to one authoritative node while reads fan out across many followers. Adds the always-compiled, dependency-free, WASM-safe [`replication`](src/replication/mod.rs) module — the **WAL-based MAIN / REPLICA** substrate plus its read-scaling story — in three layers. **(1) the log** ([`wal`](src/replication/wal.rs)) — a [`WriteAheadLog`](src/replication/wal.rs) is an append-only, in-memory log of [`WalRecord`](src/replication/wal.rs)s, each a [`WalOp`](src/replication/wal.rs) (the *write* half of [`StorageBackend`](src/storage/backend.rs) — `Put` / `Delete` / `PutBatch`, since reads never replicate) stamped with a strictly increasing [`Lsn`](src/replication/wal.rs) (log sequence number; [`Lsn::ZERO`](src/replication/wal.rs) is the "nothing yet" sentinel, the first record is `Lsn(1)`). The log retains records as a contiguous suffix: a checkpoint ([`truncate_through`](src/replication/wal.rs)) drops a prefix every follower has applied while the high-water `last_lsn` keeps climbing, and [`can_serve_since`](src/replication/wal.rs) reports whether a given follower can still be served incrementally or has lagged past the retained window. **(2) the MAIN node** ([`primary`](src/replication/primary.rs)) — a [`Primary`](src/replication/primary.rs) wraps a backend and **tees every write into the log** (the data write and the log append happen together, so the log is a faithful history), returning the assigned `Lsn`; reads delegate straight through. Followers pull the suffix they need via [`replicate_since`](src/replication/primary.rs), and an operator reclaims memory via [`checkpoint`](src/replication/primary.rs). **(3) the REPLICA node** ([`replica`](src/replication/replica.rs)) — a read-only [`Replica`](src/replication/replica.rs) serves reads (point load at any number of replicas to scale read throughput) and replays records in `Lsn` order via [`apply`](src/replication/replica.rs)/[`apply_stream`](src/replication/replica.rs), enforcing **strict in-order replay** (a record beyond `applied_lsn + 1` is rejected with [`ReplicationError::LsnGap`](src/replication/error.rs) and leaves state untouched, so a follower never silently diverges) and **idempotent re-application** (a record at or below `applied_lsn` is a safe no-op, so overlapping stream windows are harmless); its `put`/`delete`/`put_batch` exist only to refuse with [`ReplicationError::ReadOnly`](src/replication/error.rs). The sync loop is *ask-replay-advance*: `replica.apply_stream(primary.replicate_since(replica.applied_lsn())?)?`. Because each replica owns its own `applied_lsn` cursor, followers may sit at different positions; a follower that lagged past a checkpoint is told to full-resync via [`ReplicationError::Truncated`](src/replication/error.rs). Like the planner (`00085`–`00089`), MVCC (`00081`), and authz (`00094`) engines in their early tasks, this is the replication **substrate** — log, roles, replay semantics — and is **not yet wired into the executor / HTTP API / Bolt session**, nor does it ship a network transport: `replicate_since` hands back owned records a caller streams over whatever channel it likes. Keeps its own [`ReplicationError`](src/replication/error.rs) channel rather than widening the crate-wide `DrevoError`. Tests (TDD RED→GREEN): 21 inline unit (LSN monotonicity / display / next, `records_since` / `can_serve_since` / `truncate_through` invariants, op replay, primary write-tees-to-log + checkpoint truncation, replica in-order/idempotent/gap apply + read-only refusal, role classifiers) + 6 integration in [`tests/replication_tests.rs`](tests/replication_tests.rs) modelling all five target scenarios — CBT-journal MAIN-writes/replica-reads, story-editor incremental catch-up, task-manager two-replicas-independent-cursors, ERP delete + atomic batch replication, bug-tracker checkpoint-forces-resync, plus a reordered-stream gap rejection. - [x] `00096` Streaming ingestion — a knowledge graph rarely lives in isolation: domain events flow in from message brokers (a Kafka topic of journal entries, a NATS subject of task updates, a CDC tail of an upstream Postgres). Adds the always-compiled, dependency-free, WASM-safe [`streaming`](src/streaming/mod.rs) module — the **transport-agnostic ingestion engine** that turns that firehose of change events into graph mutations with broker-grade delivery guarantees — in four layers. **(1) the event** ([`event`](src/streaming/event.rs)) — an [`IngestEvent`](src/streaming/event.rs) is the decoded form of one broker message: `UpsertNode` / `DeleteNode` / `UpsertEdge` / `DeleteEdge`, each addressed by a **producer-owned [`EntityKey`](src/streaming/event.rs)** (an opaque string — a Kafka message key, a source-system primary key — *never* drevo's internal auto-increment id, which the producer cannot know and which must stay stable across re-deliveries); edges reference endpoints by *node* key (`from`/`to`) so an edge event is self-describing. Events travel as tagged JSON (`{"op":"upsert_node",…}`); upserts carry the **full** desired state (last-writer-wins, no partial patches) so replaying one converges on the same state. **(2) the broker** ([`source`](src/streaming/source.rs)) — drevo bundles no Kafka/NATS client (that would drag a heavyweight, non-WASM dependency into an always-compiled crate); instead a partition is abstracted behind the [`StreamSource`](src/streaming/source.rs) trait (`poll` a batch / `commit` the durable offset / `committed` to resume from), with monotonic [`Offset`](src/streaming/source.rs)s (the Kafka partition-offset / NATS sequence model; [`Offset::ZERO`](src/streaming/source.rs) is the "before any message" sentinel). drevo ships the in-memory [`MemorySource`](src/streaming/source.rs), which models at-least-once faithfully via [`rewind_to_committed`](src/streaming/source.rs) (re-deliver everything processed-but-not-committed, as a crash / rebalance would); a deployment implements the trait over `rdkafka`, `async-nats`, an HTTP long-poll, or a CDC tail. **(3) the sink** ([`sink`](src/streaming/sink.rs)) — decoded events land in an [`IngestSink`](src/streaming/sink.rs) (the seam that actually mutates state — keeping it behind a trait is what lets the engine stay dependency-free, the same reasoning replication applies via [`StorageBackend`](src/storage/backend.rs)). The reference [`MemoryGraphSink`](src/streaming/sink.rs) materializes the stream into a key-addressed node/edge map, demonstrates the **idempotency contract** (upsert = create-or-replace, delete-of-absent = no-op), and offers opt-in strictness ([`reject_keys`](src/streaming/sink.rs), [`require_edge_endpoints`](src/streaming/sink.rs) for referential integrity); a deployment implements the trait over a live [`Drevo`](src/db.rs) handle. **(4) the engine** ([`consumer`](src/streaming/consumer.rs)) — an [`IngestConsumer`](src/streaming/consumer.rs) drives a source into a sink: [`run_once`](src/streaming/consumer.rs) polls a bounded batch, decodes each payload, applies it, and commits the high-water offset; [`run_to_idle`](src/streaming/consumer.rs) repeats until the partition drains. Two failure modes (an undecodable payload → [`StreamError::Parse`](src/streaming/error.rs), a sink rejection → [`StreamError::Sink`](src/streaming/error.rs)) are routed by an [`ErrorPolicy`](src/streaming/consumer.rs): `Halt` stops on the first bad message (still committing the clean prefix so a fix can resume past it), while the default `DeadLetter` quarantines the raw bytes in a [`DeadLetter`](src/streaming/consumer.rs) queue and carries on. A `resume_after` watermark plus the idempotent events make at-least-once **replay-safe**: a window re-delivered after a crash converges on the identical graph with no duplicates. A [`Transport`](src/streaming/mod.rs) label (`Kafka`/`Nats`/`Cdc`/`InMemory`, with `is_durable`) tags a source for logs / metrics, the way [`Role`](src/replication/mod.rs) labels a replication node. Like the replication (`00095`), authz (`00094`), planner (`00085`–`00089`), and MVCC (`00081`) engines in their early tasks, this is the ingestion **substrate** — event model, broker/sink seams, offset/error/idempotency machinery — and is **not yet wired into the executor / HTTP API / Bolt session**, nor does it bundle a concrete broker client. Keeps its own [`StreamError`](src/streaming/error.rs) channel rather than widening the crate-wide `DrevoError`. Tests (TDD RED→GREEN): 27 inline unit (event JSON round-trip / defaults / key accessor / classifiers / malformed rejection, offset monotonicity + display, source poll-batch / commit-forward-only / rewind-redelivery, sink last-writer-wins / idempotent-delete / reject / dangling-endpoint, consumer apply-and-commit / batching / dead-letter-parse + dead-letter-sink / halt / idempotent-replay-after-crash / resume-skip / empty-noop, transport labels + durability) + 8 integration in [`tests/streaming_tests.rs`](tests/streaming_tests.rs) modelling all five target scenarios — CBT-journal entries+tags materialized live, story-editor revisions + scrapped-scene deletion, task-manager 50-event high-volume drain in batches, ERP CDC out-of-order edge dead-lettered then replayed once endpoints exist, bug-tracker corrupt-payload quarantine, plus at-least-once idempotent replay after a crash and halt-policy commits-clean-prefix. - [x] `00098` **Built-in graph algorithms — PageRank, Dijkstra, community detection (Louvain)** — drevo already shipped the *local* traversal algorithms (BFS / DFS / weighted **Dijkstra** shortest path / subgraph extraction) in [`traversal`](src/traversal.rs); this task adds the two *global* whole-graph analytics algorithms a graph database is expected to provide, in a new always-compiled, dependency-free, WASM-safe [`algorithms`](src/algorithms/mod.rs) module. Both run over an in-memory [`AdjacencyList`](src/algorithms/mod.rs) snapshot of the entire graph — unlike the per-node closures the local traversals use, a global algorithm needs the whole node set + adjacency at once, so the caller materialises the snapshot first (the [`undirected`](src/algorithms/mod.rs) projection sums reciprocal edges and separates self-loops for community detection; edge weights are read from [`Edge::weight`](src/model.rs) as non-negative link strengths, negatives clamped to `0.0`). **(1) PageRank** ([`pagerank`](src/algorithms/pagerank.rs)) — weighted power iteration of the random-surfer Markov chain: rank flows along out-edges proportionally to edge weight, dangling nodes (no out-edges) redistribute their mass uniformly so total rank stays `1.0` every step, and `1 - damping` teleports uniformly. A validated [`PageRankConfig`](src/algorithms/pagerank.rs) (`damping ∈ (0,1)` default `0.85`, `max_iterations` default `100`, L1 `tolerance` default `1e-6`) drives convergence; [`PageRankResult`](src/algorithms/pagerank.rs) reports `(node_id, rank)` pairs (plus `ranked()` sorted most-central-first), the iteration count, and whether it converged. **(2) Louvain community detection** ([`louvain`](src/algorithms/louvain.rs)) — greedy multi-level modularity optimisation (Blondel et al. 2008): a *local-moving* phase greedily moves each node into the neighbouring community of greatest modularity gain, then an *aggregation* phase collapses each community into a super-node (intra-community edges → self-loop, inter-community edges summed, total edge weight conserved across levels) and repeats until no node moves. A validated [`LouvainConfig`](src/algorithms/louvain.rs) (`resolution` default `1.0` — higher favours more/smaller communities — and a `max_levels` safety cap) drives it; [`LouvainResult`](src/algorithms/louvain.rs) reports each node's contiguously-numbered community, the final modularity, and the number of levels. Fully **deterministic** (nodes always processed in stable ID order, no randomisation). Both are exposed on the database facade — [`Drevo::pagerank`](src/db.rs) / [`Drevo::louvain_communities`](src/db.rs) — mirroring the existing [`Drevo::shortest_path`](src/db.rs) Dijkstra wiring: each builds the snapshot from `collect_all_nodes`/`collect_all_edges` and runs the pure algorithm. Config is validated at construction through the module's own [`AlgorithmError`](src/algorithms/mod.rs) channel (invalid damping / iterations / tolerance / resolution) rather than widening the crate-wide `DrevoError`, so the facade methods themselves fail only on a storage scan — and the algorithm core stays infallible. **Full Cypher `CALL gds.*` procedure syntax is deliberately out of scope** — the Cypher parser has no `CALL` / `YIELD` clause yet (a separate, larger task building procedure infrastructure); these algorithms ship as first-class Rust + facade methods now, the way Dijkstra (`shortest_path`) already was. ### Phase 16 — Python Graph-RAG SDK

> Goal: a first-class Python package (`drevo-py`) optimised for **graph-RAG (Retrieval-Augmented Generation over a knowledge graph)** use cases. The package wraps the native `Drevo` storage handle through PyO3, exposes ergonomic helpers (`Retriever`, `expand_neighborhood`, `to_text`, batch ingest of LangChain `Document` lists), and ships under three test layers (unit / integration / e2e) so RAG pipelines have the same correctness guarantees as the Rust core. The graph-RAG framing — not generic "Python bindings" — is what differentiates this phase from a thin FFI wrapper.
>
> Phase 16 cleanly **supersedes** the placeholder `00100` "Python SDK" entry in Phase 15. It runs **in parallel** with Phase 10 (Cypher) and Phase 12 (vector storage): the API surface is designed against today's Rust API and grows as Cypher + vector land. Initial cut (`00115`) targets the existing graph + FTS surface; later tasks (`00120` e2e) cover Cypher queries from Python and vector-aware retrieval once Phase 12 ships.
>
> **Why graph-RAG specifically?** RAG pipelines built on flat vector stores lose structural context (who-wrote-what, which-task-blocks-which, character-co-occurrence). A graph-native retriever can expand a similarity hit into its neighbourhood and feed that neighbourhood to the LLM as connected context — the canonical drevo value-add. This phase encodes those idioms as first-class Python helpers so embedders do not have to re-implement them per project.
>
> **Cross-cutting acceptance criteria for every Phase 16 task** (mirrors Phase 8.5 discipline):
>
> - Three test layers per `drevo-tdd` skill spec: unit (one function, mocked deps), integration (real `Drevo` instance, real redb file in a tempdir, no network), e2e (LangChain `Document` list → ingest → embed-stub → retrieve → format). Every public Python symbol has tests in **all three** layers.
> - `pytest -q` runs green on the Python CI matrix (`00122`).
> - `mypy --strict` clean on the public API surface (type stubs `.pyi` shipped alongside the wheel).
> - `ruff` + `black --check` clean.

### Phase 17 — Keyword Analytics & Lexical Search

> Goal: turn the text already stored in node/edge properties and labels into a first-class **lexical analytics** surface — better relevance ranking, salient-term extraction, and faceted "group by keyword" aggregation. The headline insight is that drevo already owns most of the machinery: the FTS module computes **TF-IDF** over a **trigram inverted index** (task `00017`), the Cypher executor already supports **`GROUP BY`** aggregations (`00066`) and the **scalar-function** extension pattern (`similar(...)`, `00077`), and the **vector module** (`00075`–`00079`) provides cosine similarity + HNSW. This phase composes those into a keyword pipeline rather than building net-new subsystems. Every task is **pure-Rust / dependency-free** (BM25, Porter stemming, RAKE are all stdlib-only); no NLP crate is pulled in.
>
> The pipeline decomposes into three independently-shippable layers: **(1)** upgrade the ranking function, **(2)** extract keywords, **(3)** collapse near-duplicate keywords and expose the faceted group-by. The five target domains all benefit: recurring CBT themes across journal entries, bug clusters by description terms, story motif tracking, task auto-tagging, ERP document faceting.

- [x] `00131` **BM25 relevance ranking (upgrade FTS TF-IDF → Okapi BM25)** — drevo's FTS today ranks by plain TF-IDF (`00017`/`00041`); BM25 is the modern standard (Lucene / Elasticsearch / Tantivy default) and is strictly better on two axes plain TF-IDF lacks: **term-frequency saturation** (the `k1` parameter — the 10th occurrence of a term must not count 10×) and **document-length normalization** (the `b` parameter — a long document is not relevant merely because it is long). Adds the persisted statistics BM25 needs to the FTS index — **per-document token length** and a running **average document length** — maintained on every insert/update/delete alongside the existing posting lists (a small additive index change; cascade-on-delete like the other indexes). Ranking becomes `Σ IDF(qᵢ) · (tf·(k1+1)) / (tf + k1·(1 − b + b·|d|/avgdl))` with the conventional `k1=1.2`, `b=0.75` defaults (tunable). The IDF component this lands is the exact salience weight task `00132` reuses to pick candidate keywords — so this task is the foundation of the band, not just an FTS quality win. Back-compat: the existing `search_fts` API and `/search/fts` endpoint keep their shape; only the score changes (a feature flag or score-version field can keep TF-IDF available if a deterministic-baseline test needs it). Depends on `00017` (FTS index). Cites: `drevo-database` §"FTS", `drevo-tdd` (RED→GREEN with a golden-ranking corpus across the five domains). **Shipped:** [`FtsRanking`](src/model.rs) enum (`Bm25 { k1, b }` default / `TfIdf` legacy) + [`Drevo::search_fts_ranked`](src/db.rs) (the unchanged [`search_fts`](src/db.rs) now delegates with BM25 defaults); raw, repetition-preserving [`raw_trigrams`](src/fts/tokenizer.rs) for term frequency + document length; persisted per-document length (`ftslen:{id}`) maintained inside [`index_node`/`deindex_node`](src/fts/index.rs) (cascade-on-delete), with `avgdl`/`N` derived drift-free via [`corpus_stats`](src/fts/index.rs); shared [`bm25_idf`](src/fts/index.rs) helper (the salience weight `00132` reuses). Three test layers added (tokenizer/index/db units + [`tests/bm25_ranking_tests.rs`](tests/bm25_ranking_tests.rs) golden-ranking corpus across the five domains).
- [x] `00132` **`keywords()` — keyword extraction from properties / labels** — a new Cypher **scalar function** `keywords(text, k)` returning the top-`k` salient terms of a string, modelled exactly on the `similar(...)` scalar-function precedent (`00077`) so it composes everywhere a `WHERE` / `RETURN` expression already works. Pipeline: a **word-level tokenizer** (distinct from the FTS *trigram* tokenizer — keyword extraction needs words, not character n-grams) + **stopword removal** (a built-in English list to start; the language axis is an explicit follow-up) + ranking by **BM25-style IDF** (from `00131`) over the corpus, optionally **Porter-stemmed** (pure-Rust) so morphological variants fold to one term. Because `keywords()` is just an expression, **faceted "group by keyword" falls out of already-shipped machinery** with no new query surface: `MATCH (n:JournalEntry) UNWIND keywords(n.body, 5) AS kw RETURN kw, count(*) AS freq ORDER BY freq DESC`. Also extracts from **labels** (a node's `kind` / multi-label set) and arbitrary property keys. NULL-propagation discipline mirrors `00077` (a node lacking the property yields no keywords rather than erroring, so a heterogeneous scan does not abort). Depends on `00131` (IDF weighting) + `00063` (Cypher executor) + `00066` (`GROUP BY`/`UNWIND`). Cites: `drevo-architecture` §"SOLID" (the tokenizer/ranker/extractor are separable), `drevo-tdd` §"three test layers".
- [x] `00133` **Keyword-similarity grouping (collapse near-duplicate keywords) + faceting API** — exact-string `GROUP BY kw` keeps *anxiety* / *anxieties* / *anxious* as three separate facets, which defeats the theme-discovery use case. This task adds **similarity-collapsed** grouping with two complementary, independently-usable axes drevo already owns: **(a) lexical** — Porter stemming and/or the **existing trigram index** as a cheap edit-distance signal (catches morphological / typo variants, dependency-free, the default); **(b) semantic** — embed each candidate keyword and cluster by **cosine similarity via the existing vector module** (`00075`–`00079` / `similar()`), which catches synonyms with no shared characters (*anxiety* ↔ *worry* ↔ *dread*) — opt-in, since it needs an embedder. Surfaces a small **faceting API** (HTTP `GET /facets?kind=&property=&k=&collapse=lexical|semantic|none` and/or a Cypher procedure) that returns `[{facet, members[], count}]`, so the cross-cutting "group my graph by extracted keyword" query is one call rather than a hand-rolled `UNWIND`. The lexical-vs-semantic split is stated explicitly so the two are not conflated: lexical is form-based and free; semantic is meaning-based and reuses the vector subsystem. Depends on `00132` (`keywords()`); the semantic path additionally depends on `00075`–`00079` (vector search). Cites: `drevo-database` §"FTS" + the vector-search design, `drevo-architecture` §"Anti-Patterns" (no premature merge of the two similarity axes). **Shipped:** new [`fts::facet`](src/fts/facet.rs) module — [`Facet`](src/fts/facet.rs) `{facet, members, count}` + [`FacetCollapse`](src/fts/facet.rs) (`None` / `Lexical { trigram_threshold }` / `Semantic { embeddings, cosine_threshold }`) + pure [`build_facets`](src/fts/facet.rs) using single-linkage [union-find](src/fts/facet.rs) over a shared-stem-or-trigram-Jaccard signal (lexical) or caller-supplied-embedding cosine signal (semantic, embedder-agnostic). Surfaced as [`Drevo::facets(kind, property, k, collapse)`](src/db.rs) (extracts `keywords()` per node of `kind`, collapses, returns documents-distinct counts; a node missing the property is skipped, not errored) and the HTTP `GET /facets?kind=&property=&k=&collapse=&threshold=` endpoint ([`api`](src/api.rs), `none`/`lexical` axes; `semantic` returns 400 since the server hosts no embedder). The two axes are kept strictly separate — one mode per call. Three test layers: 13 `fts::facet` unit tests + [`tests/keyword_faceting_tests.rs`](tests/keyword_faceting_tests.rs) (12 integration tests across the five domains) + 5 `GET /facets` HTTP tests. No new external dependency. **Completes Phase 17.**

**Definition of done:** `search_fts` ranks by BM25 with persisted doc-length stats; `keywords(text, k)` is callable from Cypher and returns deterministic, stopword-filtered, IDF-ranked terms for every one of the five domain scenarios; faceted group-by-keyword (exact, lexical-collapsed, and semantic-collapsed) is exercised end-to-end against a live `Drevo` graph and via the HTTP faceting endpoint; the whole band adds **no new external dependency**.

### Phase 18 — Interoperability & Migration

> Goal: a turnkey path for users coming **from** an existing graph database. Phase 11 already lets official Neo4j drivers talk *to* drevo over Bolt; this phase is the inbound direction — bulk-importing a user's existing data so "can I move my Neo4j to drevo?" has a one-command answer. **Architectural rule:** `drevo` (the database + its bindings) must know *nothing* about Neo4j — every importer lives outside the `drevo` package and depends on it, never the reverse.

- [x] `00134` **Neo4j → drevo migration tool** — `tools/neo4j-to-drevo/`. A **standalone package** (`neo4j_to_drevo`) that depends on `drevo` while `drevo` stays completely Neo4j-unaware (one-way dependency). Its engine `migrate(source, db, *, config=None)` is **source-agnostic**: it consumes any `GraphSource` (a `nodes()`/`relationships()` iterator pair yielding `SourceNode`/`SourceRelationship` records), so the whole label→`kind` + unique-title + property-coercion + edge-wiring path is unit-tested with an in-memory fake and **no live Neo4j**. Two source adapters feed the same engine: an **offline dump → load** path (`neo4j_to_drevo.apoc.ApocJsonSource` reads an `apoc.export.json.all` JSON-Lines dump straight off disk, pure stdlib, no driver — a graph migrates long after the source Neo4j is gone) and a **live Bolt** path (`neo4j_to_drevo.bolt.Neo4jSource`, `MATCH (n) RETURN n` / `MATCH ()-[r]->() RETURN r`, needing the `neo4j` package as an opt-in extra `pip install neo4j-to-drevo[live]`). The CLI exposes three single-purpose phases: `dump` (stream a live Neo4j to a local JSON-Lines file over Bolt), `import … --dry-run` (read + map + validate against a throwaway in-memory drevo and report what *would* happen, writing nothing), and `import` (the real load); `import` picks its source with a mutually-exclusive `--apoc-json` / `--neo4j-uri` flag. Reconciles the two structural mismatches between the models: Neo4j *label sets* fold into drevo's single `kind` (joined; full set preserved under reserved `_labels`), and drevo's **globally-unique title** invariant is satisfied by resolving a title from configurable `title_properties` then disambiguating any clash with the unique source id (so N identically-named nodes migrate with zero `DuplicateTitleError`). Neo4j temporal/spatial property values coerce to JSON-storable forms. Builds on Phase 10/11 (Cypher + Bolt parity, so a Neo4j export is semantically importable) + Phase 16 (the Python bindings the engine writes through). Cites: `drevo-architecture` §"SOLID" (engine/adapter/CLI separable + dependency direction), `drevo-tdd` §"three test layers". **Shipped:** 41 tests (37 unit + 4 integration), `ruff`/`black`/`mypy --strict` clean.

**Definition of done:** `python -m neo4j_to_drevo` imports a Neo4j graph (APOC dump or live Bolt) into a drevo database with a printed report; the mapping is lossless (labels, properties, relationship types/weights/direction) modulo documented model differences (label-set → `kind`, synthesized unique titles); the engine is driver-free and fully unit-tested without a Neo4j server; **the `drevo` package contains zero Neo4j references**.

### Re-ranking Rationale (Senior PM Lens)

Why phases 10-15 are ordered this way, rather than appended in `ex/`-source order:

1. **Preserve real progress.** Phases 1-9 (tasks `00001`–`00060`) are real, tested, merged code. New work continues numbering from `00061` — no rewrites of history.
2. **Audit before extending — and against the skill specs.** Phase 8.5 (`00103`–`00113`) is re-ranked as the **immediate next priority**. The 9.5k LOC of production code in this repo was written **before the four project skill specs existed** (`.claude/skills/drevo-{tdd,rust,architecture,database}/SKILL.md`). Those specs now codify the project's TDD workflow, error handling, ownership patterns, redb transaction rules, FFI panic safety, SOLID + anti-patterns, and storage-layer invariants — so the audit is a compliance check of existing code against the skill rules, not a vague "look for issues" pass. Each task cites the exact skill rules it verifies. Audit findings → refactor PRs → continue Phase 8/9 → Phase 10.
3. **Critical path first.** Cypher (Phase 10) blocks Bolt (Phase 11) — Bolt has nothing to execute without a working Cypher engine.
4. **Parallelizable work next.** Vector storage (Phase 12) is independent of Cypher and Bolt; a second engineer can deliver it in parallel with Phases 10-11.
5. **Foundational concurrency before optimization.** MVCC (Phase 13) is touched by every read/write path and must land before the query optimizer (Phase 14) reasons about concurrent plans.
6. **Optimization once usage exists.** The query planner (Phase 14) only pays off after real Cypher queries run on real workloads — explicit dependency on Phase 10.
7. **Production / ecosystem last but parallelizable.** Phase 15 items (MCP, Web UI, replication, SDK, fuzz, algorithms, docs, CDC) run independently and concurrently. MCP and Web UI deliver visible value early.
8. **Risk weighting.** Phase 13 (MVCC) carries highest risk — schedule with buffer. Phase 12 (vector) is novel but isolated — failure mode is contained. Phase 11 (Bolt) is a well-documented protocol — low implementation risk once Cypher works.
9. **Quality gate between Cypher and Bolt.** Phase 10.5 (`00123`–`00128`) is **not skippable** — it is the *only* moment in the roadmap where drevo's Cypher implementation can be diffed against a reference (Neo4j Community) before official drivers see it. Skipping it means `cypher-shell` users get silently-wrong answers, which is the failure mode most expensive to recover from (broken client traces, no clear bug signal at the wire layer). The 8-hour nightly soak + 95 % parity diff threshold are explicit pre-conditions for *opening* Phase 11.
10. **Python SDK pulled out into a dedicated phase.** Phase 16 (`00114`–`00122`) supersedes the placeholder `00100` "Python SDK" entry. The SDK is reframed as a **graph-RAG-first** package (`Retriever`, `Context.to_text`, document ingest helpers) rather than a thin FFI wrapper, ships three test layers per `drevo-tdd`, mirrors its API surface into the KG so the `drevo-mcp` server can answer "where is the Python API?" via MCP tools, and gates every PR on a Python × OS CI matrix. Runs **in parallel** with Phase 10 (Cypher) and Phase 12 (vector) because the API surface is designed against today's Rust API and grows as those phases land — no critical-path block, parallelisable from `00114` RFC onwards.

## Coding Conventions

### Language

- **All code comments, documentation, README, and commit messages — English only**

### Rust style

- Edition 2021, MSRV latest stable
- `cargo fmt` before every commit
- `cargo clippy -- -W clippy::all` with zero warnings
- No `unwrap()` / `expect()` in library code — `Result` only
- `unwrap()` allowed only in tests and benchmarks
- No `unsafe` without explicit justification

### Naming

- Modules: `snake_case` — Files: `snake_case.rs`
- Structs/traits: `PascalCase` — Functions: `snake_case`
- Constants: `SCREAMING_SNAKE_CASE` — Type aliases: `PascalCase`

### Errors

Use `thiserror` for all error definitions. `Result<T>` type alias everywhere.

### Serialization

- Internal data (KV store): `bincode` — compact, fast
- Configs and dumps: `serde_json` — human-readable
- All persistable structs: `#[derive(Serialize, Deserialize)]`

### Testing

- Every public method — at least 1 test
- Edge cases mandatory: empty graph, single node, cycles
- Storage tests parameterized by backend (MemoryBackend, RedbBackend)
- Benchmarks with `criterion`
- **Scenario integration tests**: each use case (CBT, story editor, task manager, ERP, bug tracker) gets a dedicated test file that exercises the full API through realistic workflows
- Scenario tests validate that `kind`/`properties`/`edges` patterns work end-to-end for each domain

### Git

- Format: `type(scope): description [task_id]`
- Types: `feat`, `fix`, `test`, `bench`, `docs`, `refactor`, `chore`

## MCP Server (Planned)

A planned `drevo-mcp` stdio binary will expose drevo as a [Model Context Protocol](https://modelcontextprotocol.io) server for Cline, Claude Code, and other MCP-compatible AI clients. The binary uses embedded storage (no Docker required) and is configured via the host's MCP settings file:

```json
{
  "mcpServers": {
    "drevo": {
      "command": "/path/to/drevo-mcp",
      "env": { "DREVO_DATA_DIR": "~/.drevo/data" }
    }
  }
}
```

The MCP server will expose node CRUD, edge CRUD, traversal, FTS, and (after Phase 10) Cypher query tools — enabling an AI agent to read and write the knowledge graph as part of a conversation.

**After Phase 16 (`00121`)** the MCP server additionally exposes Python-API introspection tools — `python_api_describe`, `python_api_examples`, `python_api_list` — backed by Python symbol entities mirrored into the KG by the `drevo-py` build pipeline. This means an AI client (Cline, Claude Code, Claude Desktop) can answer "how do I open a drevo from Python?" by querying the MCP server directly, without external docs.

Tracked as task `00090` (Phase 15); Python-API tools tracked as task `00121` (Phase 16).
