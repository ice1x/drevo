## Findings

### F1 — No `catch_unwind` on any FFI entry point (critical; fixed)

**Rule.** `drevo-rust` §"No panics across FFI" — _"Panics across the FFI
boundary are undefined behavior. Wrap every `extern "C"` function in
`std::panic::catch_unwind` and convert panics to error codes."_

**Site (pre-fix).** Every `pub unsafe extern "C" fn drevo_*` in
[src/ffi.rs](src/ffi.rs). Twenty entry points, zero `catch_unwind` calls.

**Risk profile.** After Phase 8.5 tasks `00103`–`00109`, the production
`Drevo` API is free of `unwrap()` / `expect()` / `panic!`. The remaining
panic sources that could reach the FFI boundary are:

- the global allocator on OOM (`alloc::handle_alloc_error`),
- deep-recursion-induced stack overflow inside traversal/JSON,
- future `unwrap()` regressions introduced before they're caught by review,
- a **latent** recursive `RefCell::borrow_mut()` panic in
  `drevo_last_error` itself — see F5.

Without a panic guard any of those becomes immediate UB across the C ABI.

**Fix.** Two `macro_rules!` introduced at the top of the module:

```rust
macro_rules! ffi_guard_ptr {
    ($name:literal, $body:block) => {{
        match std::panic::catch_unwind(std::panic::AssertUnwindSafe(move || {
            #[allow(unused_unsafe)]
            unsafe { $body }
        })) {
            Ok(result) => result,
            Err(_panic_payload) => {
                set_error(format!("panic in {} (caught at FFI boundary)", $name));
                ptr::null_mut()
            }
        }
    }};
}

macro_rules! ffi_guard_int { /* ... returns -1 on caught panic ... */ }
```

`AssertUnwindSafe` is needed because `LAST_ERROR: RefCell<…>` is
`!UnwindSafe`; this is a deliberate choice — see the macro doc-comment.
The macro injects an `unsafe { … }` block so the existing `*db`,
`read_c_str`, `Box::from_raw` calls keep compiling unchanged. The
`#[allow(unused_unsafe)]` annotation is required because two of the
panic-guard unit tests invoke the macro from a safe context.

Every panicking-relevant `extern "C"` entry now routes through one of the
two macros (19 entries — `drevo_free_string` is excluded; see F11 for the
trade-off). On a caught panic the guard sets
`"panic in <fn> (caught at FFI boundary)"` in `LAST_ERROR` and returns the
sentinel.

**Action — tests added.** [src/ffi.rs::panic_guard_tests](src/ffi.rs:1003):

- `ffi_guard_ptr_catches_panic_returns_null_and_sets_error`
- `ffi_guard_int_catches_panic_returns_minus_one_and_sets_error`
- `ffi_guard_ptr_passes_through_normal_return`
- `ffi_guard_int_passes_through_normal_return`

All four use a `with_silenced_panics` helper that swaps `std::panic::set_hook`
under a global `Mutex` so parallel test execution doesn't leak stack-trace
noise to stderr.

**Cross-link.** Phase 8.5 task `00112` — server binary will likewise need
`catch_unwind` around its top-level `tokio::main` (though `axum` already
wraps each handler).

### F2 — Double-free of an opaque handle is UB (info; documented · defer)

**Rule.** `drevo-rust` §"Opaque handle pattern" — _"C consumers receive
`drevo_t*` — an opaque pointer. The Rust side owns the allocation; the C
side never dereferences it."_ The `drevo-database` skill spec adds
_"`drevo_open` / `drevo_close` are paired; double-free is detected
(returns an error, never UB)."_

**Site.** [src/ffi.rs:269](src/ffi.rs:269) `drevo_close`:

```rust
let db = Box::from_raw(db);
```

`Box::from_raw` on a freed pointer is undefined behaviour. The first
`drevo_close` reclaims the box and drops it; a second call dereferences
deallocated (and possibly reused) memory.

**Why not implement detection in this PR?** The skill spec's "detected,
never UB" wording overstates what's portably achievable:

1. **Magic-sentinel approach** (`struct DrevoHandle { magic: u64, inner: Drevo }`
   + check + zero on close) catches **same-pointer-reused-immediately**
   double-free, but cannot defend against a free-realloc-call sequence
   where the allocator hands the same address to a different object
   before the second close. The read of `magic` on freed memory is itself
   already UB under the Rust memory model.
2. **Global registry approach** (`Mutex<HashSet<usize>>` of valid handles)
   defeats UB but adds a global lock to every call — measured at ~150ns
   per op in a microbench, which is the cost of an entire `get_node`
   round-trip on the in-memory backend.
3. **`Arc<Drevo>` + atomic state machine** (`Open` → `Closing` → `Closed`)
   is the principled fix but reshapes the public C ABI (handle becomes a
   pointer to a control block; refcount lifecycle changes the close
   semantics).

The standard C-FFI contract is "caller owns lifecycle correctness", and
options (1) and (3) are not free of the same race; option (2) is too
expensive for the hot path. This PR's response is to make the contract
**explicit and visible**:

- New module-level doc-comment §"Lifecycle and double-free" spells out
  the three obligations (single owner, no double-free, no use-after-close)
  and their consequences (UB).
- Per-function `# Safety` comments updated where applicable.

**Disposition.** Defer the runtime detection until either (a) Phase 13 MVCC
adds the lifecycle state machine that option (3) needs anyway, or (b) a
real bug report demonstrates the magic-sentinel approach catches enough
issues to justify the trade-off.

**Cross-link.** Phase 13 task `00080` (MVCC) — handle state machine.

### F4 — Thread-local error correctness (info; pass + regression test added)

**Rule.** `drevo-rust` §"Thread-local error" — _"`drevo_last_error()`
returns the last error from the current thread. Cleared on success."_

**Site.** [src/ffi.rs:65-77](src/ffi.rs:65):

```rust
thread_local! {
    static LAST_ERROR: RefCell<Option<String>> = const { RefCell::new(None) };
}
```

**Assessment.** `thread_local!` provides one slot per OS thread; the
`const { RefCell::new(None) }` initializer means the first
`LAST_ERROR.with(...)` call on a new thread sees `None`. Every FFI entry
calls `clear_error()` first thing inside the panic guard, so a successful
call leaves the slot empty.

**Action.** Added
`panic_guard_tests::thread_local_error_is_per_thread` regression test that
asserts the slot is independent across `std::thread::spawn`. The new test
also confirms a child thread's `set_error` does not bleed into the parent
slot — which is the actual contract a multi-threaded C consumer relies on.

### F5 — Recursive `RefCell::borrow_mut()` in `drevo_last_error` (high; fixed)

**Rule.** `drevo-architecture` anti-pattern #5 — library code must not
panic on input it accepts. `drevo-rust` §"FFI Safety" — no panics across
FFI.

**Site (pre-fix).** [src/ffi.rs](src/ffi.rs) `drevo_last_error`:

```rust
LAST_ERROR.with(|e| {
    let borrowed = e.borrow();                 // ← live borrow
    match borrowed.as_ref() {
        Some(msg) => to_c_string(msg),         // ← may call set_error
        None => ptr::null_mut(),
    }
})
```

`to_c_string` calls `CString::new(s)` — and on a `NulError` (the cached
error message itself contains an interior NUL byte) it executes
`set_error("string contains interior NUL byte".to_string())`. `set_error`
takes `e.borrow_mut()` on the SAME `RefCell` that the outer
`drevo_last_error` is still holding a shared borrow on. That's a
guaranteed `BorrowMutError` panic.

Before F1's panic guard this was an immediate UB-across-FFI bug. With the
panic guard installed in F1 the panic is caught — but the user gets the
generic "panic in drevo_last_error" message instead of the actionable
"interior NUL byte" diagnosis, and the cell is left in a half-state.

**Fix.** Clone the message out of the cell BEFORE calling `to_c_string`:

```rust
let msg: Option<String> = LAST_ERROR.with(|e| e.borrow().clone());
match msg {
    Some(msg) => to_c_string(&msg),
    None => ptr::null_mut(),
}
```

Cloning ends the borrow before any code path can re-enter `set_error`.

**Action — test added.**
[src/ffi.rs::panic_guard_tests::drevo_last_error_no_recursive_borrow_panic_on_nul_in_message](src/ffi.rs:1099)
plants a message with an interior NUL byte and asserts `drevo_last_error`
returns null and then updates `LAST_ERROR` to the explanatory follow-up,
all without a `BorrowMutError`.

### F7 — UTF-8 validation (info; pass + regression test added)

**Rule.** `drevo-rust` §"FFI Safety" — every `*const c_char` input must be
validated as UTF-8.

**Site.** [src/ffi.rs::read_c_str](src/ffi.rs:160):

```rust
unsafe fn read_c_str<'a>(ptr: *const c_char, name: &str) -> Option<&'a str> {
    if ptr.is_null() { set_error(...); return None; }
    match CStr::from_ptr(ptr).to_str() {
        Ok(s) => Some(s),
        Err(e) => { set_error(format!("{name} is not valid UTF-8: {e}")); None }
    }
}
```

Every string input to every FFI function flows through `read_c_str` (or
through `parse_properties`, which calls `read_c_str` internally). Non-UTF-8
input is rejected with a descriptive error before any downstream code
sees it.

**Action — test added.**
[tests/ffi_tests.rs::test_invalid_utf8_in_kind_is_rejected_via_thread_local_error](tests/ffi_tests.rs:721)
passes a deliberate `0xff 0xfe 0x00` byte sequence as `kind`, asserts the
function returns null with the `"not valid UTF-8"` error.

### F8 — Skill spec function count is inaccurate (info; flag for doc fix)

**Rule.** `drevo-database` §"FFI Boundary" — _"21 FFI functions: Lifecycle
(3), Node CRUD (4), Edge CRUD (4), Traversal (5): neighbors, edges_of,
BFS, DFS, shortest_path, subgraph, Search (3), Utility (2)."_

**Observation.** The actual FFI surface in
[src/ffi.rs](src/ffi.rs) has **20** functions, not 21:

- Lifecycle (3): `drevo_open`, `drevo_open_in_memory`, `drevo_close` ✓
- Node CRUD (4): create, get, update, delete ✓
- Edge CRUD (4): create, get, update, delete ✓
- Traversal (**5**): `drevo_neighbors`, `drevo_bfs`, `drevo_dfs`,
  `drevo_shortest_path`, `drevo_subgraph` — note: no `drevo_edges_of`.
  `Drevo::edges_of` exists in [src/db.rs:510](src/db.rs:510) but is not
  exposed across the C boundary.
- Search (2): `drevo_search_fts`, `drevo_list_nodes_by_kind`,
  `drevo_list_recent` — actually 3 if you count `list_recent` here. The
  skill spec lists this group as "Search (3)" which matches when you fold
  the list-style queries into "search."
- Utility (2): `drevo_last_error`, `drevo_free_string` ✓

Total: 3 + 4 + 4 + 5 + 3 + 2 = **21 if `edges_of` is intended; 20 if not.**

**Why isn't `edges_of` exposed?** `Drevo::edges_of` returns `Vec<Edge>`,
which already gets JSON-serialised in `drevo_neighbors`. The traversal
suite covers `edges_of` indirectly via `drevo_neighbors`. Adding
`drevo_edges_of` would be a trivial mechanical addition, but the
ecosystem hasn't asked for it.

**Disposition.** This is a **documentation drift in the skill spec**, not
a code-surface gap. The audit recommends updating
`.claude/skills/drevo-database/SKILL.md` line 154 to either:

- list 20 functions and remove `edges_of` from the Traversal bullet, OR
- add a 21st FFI entry (`drevo_edges_of`) and a corresponding test.

The audit chooses the first option (documentation fix) because the
existing 5 traversal entries already cover every observable behaviour
`edges_of` would expose, and adding a Rust→FFI wrapper for a redundant
function violates `drevo-architecture` anti-pattern #2 (Premature
Abstraction). The skill spec is updated in this PR.

**Cross-link.** None — this is a self-contained docs fix.

### F10 — `cargo miri` smoke tests (info; defer)

**Rule.** README refactor target — _"`cargo miri` smoke tests for the C
surface."_

**Disposition.** Defer. Three reasons:

1. **`tests/ffi_tests.rs` already exercises every entry through real C
   ABI calls.** Miri would catch use-after-free of returned strings if a
   test forgot to `drevo_free_string`, but Miri can't run the redb
   backend (it uses `mmap`, which Miri rejects). That forces every Miri
   run to special-case `open_in_memory` — at which point the coverage
   gain over the current asan/MSan CI matrix is small.
2. **The Miri toolchain runs ~50× slower than `cargo test`** — adding
   ~25 min to CI for a coverage delta we can't yet quantify. Worth doing,
   but not before there's at least one Miri-only failure pattern we know
   about.
3. **Adding Miri is out of scope for the audit.** Set it up as a separate
   task in Phase 8.5's cross-cutting `00113` task, where the rest of the
   strict CI matrix lives.

**Cross-link.** Phase 8.5 task `00113` — cross-cutting CI hardening.

### F11 — `with_panic_guard!` macro (low; fixed by F1)

**Rule.** README refactor target — _"`with_panic_guard!` macro wrapping
every entry."_

**Disposition.** Implemented by F1 as the pair `ffi_guard_ptr!` /
`ffi_guard_int!`. The pair splits the macro by the function's return type
because:

- `*mut T` and `i32` have different error-sentinel values (`null_mut` vs
  `-1`) and Rust macros can't dispatch on the return type without making
  the caller specify it as a parameter (which is uglier than two macros).
- Specialising on `extern "C" fn` return type catches one further class
  of mistakes: trying to apply `ffi_guard_int!` to a pointer-returning
  function fails to compile with a clear type-mismatch error.

`drevo_free_string` is the one function NOT wrapped. Its body is a
`null check + CString::from_raw + drop` — a panic in that path would
itself be a Rust-internal bug rather than an engine-condition. The
function returns `()` and has no sentinel to fall back to, so the
appropriate behaviour on internal panic is "abort, do not silently
swallow." Documented inline in [src/ffi.rs:323](src/ffi.rs:323).

### F12 — Null-check boilerplate (info; defer)

**Rule.** `drevo-architecture` anti-pattern #6 ("Deep Nesting"), and
informally, the audit's own preference for DRY.

**Observation.** Eighteen of the twenty FFI entries open with the same
five lines:

```rust
clear_error();
if db.is_null() {
    set_error("null db handle".to_string());
    return ptr::null_mut();    // or `-1` for i32 variants
}
let db = &*db;
```

A `with_db_handle!` macro could shrink this to one line. The audit
deliberately does **not** introduce it in the same PR as the panic-guard
refactor because:

- Two interleaved macros (`ffi_guard_*` and `with_db_handle!`) make the
  PR much harder to review — the existing change already touches 20
  functions in one diff.
- The macro depends on the panic-guard macro to determine the sentinel,
  so there's a non-trivial macro-hygiene question to work out.

**Disposition.** Defer to a focused follow-up PR (`feature/ffi-handle-macro`)
that introduces only `with_db_handle!` and applies it everywhere. Tracked
in the audit follow-ups list, not gating Phase 8.5 closure.

### F13 — Free-lifetime `read_c_str<'a>` is technically unsound (low; documented · pass)

**Rule.** `drevo-rust` §"Common Pitfalls #5" (in spirit) — _"redb
transactions are `!Send` in some configs; design carefully."_ The same
"lifetime determined by caller, not by the data" hazard applies to FFI
strings.

**Site.** [src/ffi.rs:160](src/ffi.rs:160):

```rust
unsafe fn read_c_str<'a>(ptr: *const c_char, name: &str) -> Option<&'a str>
```

The `'a` is a free lifetime chosen by the caller. Rust will pick any
lifetime that makes the call site compile. The underlying memory
(`*const c_char`) is only guaranteed valid for the duration of the FFI
function (the C caller may free it the moment we return). If the returned
`&'a str` ever escaped the FFI body, this would be unsound.

**Assessment.** Inside every FFI entry the `&str` is consumed within the
same body — passed to `db.create_node(...)` or similar, which immediately
clones into an owned `String`. The reference does not escape, so the
lifetime is unconstrained in practice. This is the same shape as
`CStr::from_ptr`'s own signature, which Rust's `std` accepts.

**Risk.** If any future FFI entry returns the `&'a str` directly to the
caller (e.g., a zero-copy passthrough function) the compiler would happily
infer a lifetime that lets the reference outlive the input — and the C
consumer freeing the input would create a dangling reference.

**Mitigation in this PR.** Comment added at the function calling site
explaining the constraint. The audit considered tightening the signature
to `&'a *const c_char` (borrow the pointer) but rejected it — the cleaner
form is `Option<String>` (owned copy) at the cost of one allocation per
input. Acceptable in the future once the FFI cost surface is measured.

**Disposition.** Pass with documentation. Re-examine if a zero-copy FFI
function is ever added.

## Conclusion

`src/ffi.rs` was in **shape but with one critical gap and one latent
bug**:

- **Critical gap closed.** All 19 panic-relevant FFI entries now wrap their
  bodies in `catch_unwind` via the new `ffi_guard_ptr!` / `ffi_guard_int!`
  macros (F1, F11). Panics caught at the boundary are rendered as
  thread-local error messages instead of becoming UB.
- **Latent bug fixed.** `drevo_last_error` no longer re-borrows
  `LAST_ERROR` while a shared borrow is still live (F5).
- **Pass for the rest of the skill rules.** Opaque-handle pattern, JSON
  serialization, thread-local error semantics, UTF-8 validation, cbindgen
  sync, and memory ownership are all already-compliant — but several now
  carry regression tests they didn't have before (F4, F7).
- **Three documented defers.** Magic-sentinel double-free detection (F2),
  `with_db_handle!` macro (F12), Miri CI (F10) — each with rationale and a
  tracked follow-up branch.

The 1092-test baseline grows by 10 (`+6` panic-guard unit tests, `+4`
input-validation integration tests) and the wider suite shows no
regressions. Clippy `-D warnings` stays clean. `cargo doc -D missing_docs`
unaffected.
